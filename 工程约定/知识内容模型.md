# 知识内容模型

这是 MEMORY／DOCUMENT／SKILL 的唯一内容模型与模板入口。适用于已授权的知识整理和人工复核；不自动同步 Native Memories，不修改个人技能，不批量改写旧 Asset。旧文件不因缺少这些标题被 Scanner 拒绝。

区分两类权威：

- 机器资格字段仍以 `asset/schema.ts` 的 Zod Schema 为准，本文不复制出另一个可独立变化的 Schema。
- 内容模型定义知识应回答的问题，模板是同一模型的 Markdown 表达。先由整理和人工审核使用，不因旧文件缺少标题而让 Scanner 拒绝既有 Asset。

本期不把正文解析成新的数据库实体，不在 YAML 中增加 `approved`、`confidence`、`version`、`supersedes` 等字段，不自动认证来源。若以后确实需要机器查询某字段，再单独评估 Schema 演进。

## 最小结构

| 内容项 | 要回答的问题 | 填写规则 |
|---|---|---|
| 当前结论／内容 | 现在应知道或执行什么 | 必须清楚；MEMORY 写判断，DOCUMENT 写资料／方案，SKILL 写步骤 |
| 适用条件 | 什么项目、环境、前提下适用，哪些变化需要复核 | 必须明确，不用 GLOBAL 替代语义适用条件 |
| 原因与取舍 | 为什么这样做，接受了什么代价 | 工程判断必写；资料无实际决策时说明来源即可，不编造比较过程 |
| 依据与验证边界 | 依据是什么，何时观察，验证过什么、还不知道什么 | 引用具体原件或命令结果；来源与验证分开表达，不用“已验证”概括模型推断 |
| 本次变更说明 | 改了什么，为什么旧判断不再适用，现在采用什么 | 仅修改已有判断时填写；首次新增不强制填空表 |

正文允许短写；这些是信息完整性要求，不要求每条知识铺满相同长度。`summary` 必须与当前结论一致，保留决定性的适用前提，因为 MEMORY 可能只投影摘要。

## 通用模板及类型差异

下方占位不能直接作为合法 Asset 入库。ID 必须由现有生成器生成；GLOBAL 省略 workspace，其余 Frontmatter 沿用当前 Schema。

````markdown
---
id: <生成的ast ID>
type: MEMORY
scope: WORKSPACE
workspace: <已配置的Workspace>
title: <主题>
summary: <当前结论与关键适用条件>
---

# <主题>

## 当前结论
<可直接复用的判断；DOCUMENT 可展开方案，SKILL 可列步骤>

## 适用条件
<环境与前提；发生哪些变化时需要复核>

## 原因与取舍
<可验证的理由；不编造备选方案>

## 依据与验证边界
- 来源：<实际文件／文档链接；可用时给出明确版本或观察日期>
- 已验证：<实际验证的对象、方式和结果；未运行则明确未运行>
- 未验证：<仍无法支撑的范围>

## 本次变更说明
<仅更新已有知识时保留：日期；变更原因；旧条件与新条件；替代结论或现有来源引用>
````

DOCUMENT 可保留自然章节，只需在前言或相关章节回答适用性、来源和验证边界；SKILL 在当前内容中明确触发、前置条件、步骤、验证及停止条件。三种类型共享模型，不强制把长文档改造成短 MEMORY。

Native 提供的线索可注明其来源，但不能代替支撑工程判断的当前事实。未核实内容应明确为待验证；模板存在不意味着该内容已获批准。

## 候选审阅展示模板

候选原文沿用上面的知识正文模板；聊天摘要仅帮助人快速决定如何处理，不替代完整候选。发送前读取完整候选并保留确切路径、Asset ID 和原字节 SHA-256；更新候选还需绑定正式基线 Hash。执行接受前再次核对，内容变化则重新展示确认。

在聊天正文中用 Markdown 展示以下内容，字段之间保留空行：

```markdown
**<项目名或 GLOBAL> · 知识候选**

**【标题】** <知识标题>

**【摘要】** <一到两句核心判断，保留影响决策的适用前提>

**【原因】** <建议新增／扩展／修订，以及检索比较后的增量理由>

[查看完整知识库候选](<候选文件的绝对路径>)
```

链接指向本次审阅的完整 Inbox 文件；不手动添加文件 Emoji，客户端会显示文件图标。详细来源、测试细节和验证边界留在原文，默认不展示完整 Hash，不重复播报同一摘要。检索未命中只能描述本次检索结果，不能声称全库不存在相似内容。

### 选择框与等待

正文发出后调用当前可用的 `request_user_input_async`，让摘要与选择框在同一回合呈现。问题保持简短，正文不塞入问题标题；本次 Desktop 实测标题中的换行未形成分段，不依赖其 Markdown／富文本渲染。

```json
{
  "questions": [{
    "title": "如何处理这条知识候选？",
    "options": ["接受入库", "修改", "暂存（保留文件）", "拒绝（删除候选）"]
  }]
}
```

- 接受入库：明确提交后核对本次候选 Hash，调用现行单文件确认；接受绑定完整候选，不能只绑定摘要。
- 修改：依据意见修改候选后重新展示；没有具体意见时先询问，不沿用旧确认。
- 暂存：只保留 Inbox 文件，不增加状态、提醒或调度。
- 拒绝：核对确切 Inbox 路径及本次 Hash 后直接删除该候选，无需二次确认；不删除对应正式知识。

当前采用保留按钮的交互：弹框后保持本轮等待，不发送最终回复（包括空回复），不追加无意义进度消息。可用当前等待工具等待输入；用户回答由客户端送达，不轮询文件、数据库或消息历史。等待期间界面可能持续显示“进行中”，这是 Codex 回合等待反馈，不是 Inbox 审批状态，也不需要修改 CodexMemoryOS 的 Task 状态。

用户选择后执行对应操作并结束本轮；用户中断或提出其他问题时及时处理，不强行继续等待。预选、跳过、无回复或超时不构成接受。工具不可用时退回文字选择。

验证边界：2026-09-07 当前 Desktop 会话中，结束回合后选择框消失；保持等待后，用户成功提交“接受入库”并完成确认。该等待方式是当前客户端的适配做法，不是官方承诺的永久行为；客户端升级后可重新核验。不要承诺结束回合后按钮仍然保留。
