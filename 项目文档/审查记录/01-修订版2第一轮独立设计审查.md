结论：**CONDITIONAL PASS**。

Revision 2 已经从上一轮的“知识平台 + 无损迁移平台”明显收敛为个人本地 Asset 系统：Markdown + Git 保存当前正式内容，`assets/` / `inbox/` 表达 Human-First，SQLite 只保存可重建索引和可丢失运行数据，MCP 只提供 Search/Read/Loadout/Usage，Hub 保持只读，旧 V4 只作为人工整理输入。方向正确，也没有必要恢复 Revision、Head、Publication、HumanReview、Relation、Receipt、Shadow、回滚平台或旧 Usage。

## 3. First-Principles Minimal System

### 3.1 用户真正要解决的失败

真正的产品失败只有两个：

1. Codex 在新的具体任务中不能稳定找到、读取“当前仍有用”的个人知识，导致重复分析或重复犯错。
2. Codex 生成的候选内容如果未经人处理就进入默认搜索，会污染后续任务。

Usage、Task Loadout 和 Hub 是固定要求下的可观察性与可解释性，不是知识真相；它们不能反向要求增加 Revision、审计链、迁移平台或多表状态机。

### 3.2 最小可运行闭环

```text
用户维护 Markdown
  → 正式内容位于 assets/，候选位于 inbox/
  → Node 服务扫描、校验并建立可重建 Catalog/FTS
  → Hook 由 cwd 确定可信 Workspace，并为当前 Codex turn 创建 Task
  → Codex 通过 MCP search 获取当前 Workspace + GLOBAL 的少量结果
  → Codex 通过 MCP read 读取确切 Markdown
  → Search/Read 记录非关键 Usage，Codex 显式 mark USED
  → Hub 只读展示同一批服务数据和诊断状态
  → 用户在编辑器或明确确认流程中把候选移入 assets/
```

旧知识整理是此闭环的一个输入流程，不是运行时子系统：全量盘点源文件，按当前知识主题去重/聚类，用户决定 KEEP/MERGE/REWRITE/DROP，Codex 生成 Inbox Asset，用户最终检查后再进入 assets。

### 3.3 MVP 必需组件

- 一个 Asset Repository：`assets/`、`inbox/`、Markdown、Git。
- 一个 Workspace 配置：路径最长匹配，未知 Workspace 只允许 GLOBAL。
- 一个 Node 常驻进程：Scanner、Catalog/FTS、Asset Service、Task Loadout、Usage、HTTP MCP、只读 REST、Vue 静态资源。
- 一个最小 Hook：传递可信 Workspace、内部 Task ID 和少量 DIRECT 摘要。
- 五个冻结 MCP 工具。
- 一个只读 Hub，页面不反向创造新领域对象。
- 一个临时旧知识 inventory/review/generation 流程。

### 3.4 明确非目标

- 不证明旧知识的演进、确认或关系链。
- 不迁移旧 ID、Usage、Task、Review、Relation、Receipt、Audit、Promotion。
- 不建立 Asset Revision/Head/Publication。
- 不代理模型请求，不需要模型 API。
- 不实现在线编辑、自动确认、Skill 安装、ConversationHistory、团队权限、多 Agent、知识图谱、向量库或迁移回滚平台。
- 不让 SQLite、Hub 或 Usage 成为正式知识的事实源。

### 3.5 职责去重

- Scanner 只负责文件发现、解析、Hash 和诊断；Indexer 只消费 Scanner 结果，不再解析第二遍。
- Asset Search 只负责 Workspace 资格、FTS 和排序；Context 调用它，不复制另一套搜索规则。
- Context 只决定 DIRECT/ON_DEMAND 和预算；Usage 模块独占 Usage upsert，Context 不直接造 Usage 行。
- MCP 与 REST 只是适配层，共用 Application Service，不复制业务规则。
- Hook 只做 Codex 生命周期关联和短上下文注入，不扫描文件、不连 SQLite。

## 4. P0 / P1 / P2 Findings

### 4.1 P0 Findings

#### P0-01：统一 ID 格式直接违反已冻结契约

**问题描述**

冻结格式是 `<三位业务前缀>_<Snowflake十进制字符串>`。主设计、迁移设计、Frontmatter 和 Loadout 示例全部使用无下划线的 `ast203... / tsk203... / usg203...`。

**具体失败场景**

实现者无法同时满足冻结验收和两份文档；一部分代码按 `ast_` 校验，另一部分按 `ast` 生成时，Scanner、MCP Schema、迁移生成和 Hub 路由会互相拒绝 ID。

**证据**

- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:323-342`：ID 格式及示例无下划线。
- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:395-425,442-456,738-770`：Frontmatter、文件名和 Loadout 示例继续使用无下划线格式。
- `项目文档/设计方案/02-旧知识人工整理方案-修订版2.1.md:347-385`：迁移生成契约同样无下划线。

**影响**

这是跨 Asset、Task、Usage、HTTP、JSON、SQLite 和人工整理的基础契约冲突，不能开始 Asset Core 实现。

**最小修正方案**

仅把所有示例、正则、类型注释统一为 `ast_<decimal>`、`tsk_<decimal>`、`usg_<decimal>`；Snowflake 数值本身仍是十进制字符串，不改任何架构。

**为什么足够**

问题只是序列化格式冲突，不需要 ID 服务、兼容层或旧 ID 映射。

#### P0-02：Workspace 的可信来源和 Read 资格没有闭合

**问题描述**

主设计让 `asset_search` 同时接收 `taskId` 和调用方传入的 `workspace`，随后按“当前 Workspace”过滤，但没有规定必须从 `task_loadout.workspace` 派生并校验。`asset_read` 只接收 `taskId + assetId`，没有写明必须重新执行 `GLOBAL OR same WORKSPACE` 资格判断。Asset 目录也重复表达 Global/Workspace，而文档没有冻结“路径与 Frontmatter 不一致”时谁是事实、是否进入索引。此外，Workspace 识别失败时设计要求只搜 GLOBAL，Task 表却把 `workspace` 定义成 NOT NULL，未定义该 Task 如何表示。

**具体失败场景**

1. 当前任务属于 Workspace A，Codex 在 MCP 参数中传入 B，Search 返回 B 的知识。
2. Codex 从旧上下文得到 B 的 `assetId`，在 A 的 task 下直接调用 `asset_read`，完整内容被返回。
3. 文件放在 `assets/workspaces/B/`，Frontmatter 却写 `workspace: A`；不同实现可能按路径或 Frontmatter 索引，导致知识进入错误任务。
4. cwd 无匹配时，Hook 要么无法创建 NOT NULL Workspace 的 Task，要么把字符串 `global` 伪装成 Workspace，产生两种实现。

**证据**

- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:270-306`：目录表达 Global/Workspace。
- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:395-425`：Frontmatter 再次表达 scope/workspace。
- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:503-547`：cwd 最长路径匹配与未知 Workspace fail closed。
- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:591-602`：Task workspace 当前为 NOT NULL。
- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:646-667`：MCP Search 请求接收 workspace，过滤规则未说明可信绑定。
- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:848-864`：Read/Mark Used 没有 Workspace 资格规则。
- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:1184-1198`：N01 只说“非法 Workspace、非法路径可识别”，没有给出一致性谓词。

**影响**

可能把跨 Workspace 知识带入错误任务，符合本轮 P0 定义。

**最小修正方案**

冻结一个单一规则：

1. Hook 依据 cwd 与 `workspaces.json` 产生可信 Workspace，并写入 Task。
2. 有 `taskId` 的 MCP 工具一律从 Task 取 Workspace；删除 `asset_search.workspace`，或只允许它与 Task 值完全相等。
3. Search、Read、Mark Used 都执行同一资格谓词：`GLOBAL OR asset.workspace = task.workspace`。
4. Task 的 `workspace` 允许 NULL；NULL 明确表示 cwd 未匹配、只能访问 GLOBAL。不要创建名为 `global` 的伪 Workspace。
5. `scope=GLOBAL` 时 Asset `workspace` 必须缺省且路径位于 `global/`；`scope=WORKSPACE` 时配置、目录名和 Frontmatter workspace 必须三者一致。
6. 任何不一致、未知 Workspace、重复 ID 或未知类型都 fail closed：文件保留，但不进入 Catalog/FTS，并进入 System Status 诊断。

**为什么足够**

复用现有 Task、Workspace 配置和 Scanner 即可，不需要 ACL、用户体系或权限服务。

### 4.2 P1 Findings

#### P1-01：Task 与 Codex 生命周期没有可执行关联，且阶段顺序隐藏依赖

**问题描述**

Task 表只有内部 `task_id`，Hook 却被要求“创建或更新 Task”，没有保存 Codex `session_id + turn_id` 的普通列，也没有说明 Stop/Interrupt 如何找到同一 Task。Search/Read 从 N03 起要求 taskId 并写 Usage，但 Task/Usage 到 N04、Hook 到 N05 才实现。

**具体失败场景**

- UserPromptSubmit 和 Stop 是两个独立 Hook 进程；没有 source correlation 列时，Stop 无法把同一 `tsk_...` 改为 COMPLETED。
- 同一 turn 的 Hook 重试可能创建两个 Task。
- N03 的真实 MCP Search/Read 没有可取得的 taskId，或为了测试而绕过最终契约。
- 多窗口同时使用时，RUNNING 记录无法确定属于哪个 Codex turn。

**证据**

- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:591-611`：Task 表没有 Codex correlation 字段。
- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:646-655`：Search 把 taskId 设为必需输入。
- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:876-890,1015-1025`：Hook 创建/更新与 status 写接口缺少关联协议。
- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:1215-1258`：MCP 先于 Task/Usage 和 Hook。
- 官方 Hooks 文档说明 UserPromptSubmit/Stop/Interrupt 都提供 turn-scoped `turn_id`，公共输入提供 `session_id` 与 `cwd`：[OpenAI Codex Hooks documentation](https://developers.openai.com/codex/hooks)。

**影响**

Task 生命周期、Usage 外键和真实 MCP 纵切都会返工。

**最小修正方案**

- Task 普通列增加 `source_session_id`、`source_turn_id`，并建立二者唯一约束；它们只是运行关联键，不是 ConversationHistory。
- 一次 UserPromptSubmit 对应一个 Task；重复 Hook 对同一 source pair 幂等返回原 taskId。
- Stop 标记 COMPLETED，Interrupt 标记 CANCELLED；SessionEnd 只清理同 session 残留 RUNNING。
- 先完成纯 Asset Service Search/Read 纵切；随后实现“最小 Task correlation + Hook”，再把真实 MCP 工具与 Usage 接上。不要让完整 Loadout/Usage 阻塞纯 Search/Read Service。

**为什么足够**

只增加两个稳定查询列和三个现有状态的转换，不引入会话正文、Task 状态机或事件账本。

#### P1-02：Snowflake 只有原则，没有可互操作的最低生成规则

**问题描述**

文档规定 bigint、固定 Epoch、单服务和时钟回退 fail fast，但没有冻结 bit layout、workerId、同毫秒 sequence 溢出或跨进程重启后的回退检测。`extractTimestamp` 又要求实现知道这些布局。

**具体失败场景**

- 不同 npm 库使用不同 Epoch/位宽，旧 ID 无法被新实现解析。
- 单毫秒超过 sequence 上限时产生重复或抛出未定义错误。
- 进程重启后系统时钟早于上次已生成时间，sequence 从零开始，可能重号。

**证据**

- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:345-376`：只给出通用接口和原则，把具体库留给实现，缺少上述生成参数。
- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:1105-1115`：测试要求唯一性、时间解析和时钟回退，但没有可据以断言的算法契约。

**影响**

IdGenerator 测试无法冻结，后续更换库可能改变所有 ID 的解析语义。

**最小修正方案**

冻结单机规则即可：一个明确的 Epoch；41-bit 毫秒时间 + 10-bit worker + 12-bit sequence；`workerId=0` 固定且不开放配置；每毫秒 sequence 从 0 到 4095，溢出等待下一毫秒；进程内 `now < lastTimestamp` 立即失败；启动时用 Asset ID 和运行库中可见 ID 的最大时间戳作为水位，当前时间早于水位时拒绝生成。bigint 只存在 IdGenerator 内部，边界一律输出带下划线字符串。

**为什么足够**

这是单进程本地规则，不需要 worker 注册、分布式锁或 ID 服务。

#### P1-03：Loadout JSON 与 Usage 的写入所有权和语义互相重叠

**问题描述**

Context 被要求为每个入选 Asset 创建 Usage 并写 usageId；Asset Search 又对每个返回结果自动记录 RECALL；Context 自身正是通过 Asset Search 选结果。文档没有说明未入选但被 Search 返回的 Asset 是否建 Usage、一次 Context resolve 是否会重复计数。JSON 模式名也与冻结的 DIRECT/ON_DEMAND 不一致，整体覆盖和终态可变性未定义。

**具体失败场景**

- 一次 Context resolve 对入选 Asset 计两次 RECALL。
- Search 返回但未进入 Loadout 的 Asset 因没有 Usage 行而无法记录 RECALL。
- 数组顺序与 `order` 字段冲突，Hub 展示顺序不确定。
- COMPLETED Task 被再次 resolve，历史 JSON 和计数被覆盖。

**证据**

- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:703-704`：Search 成功返回即记录 RECALL。
- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:711-721`：Context 又创建 Usage。
- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:738-780`：JSON 保存 usageId、order、派生 result，并使用 INJECT_SUMMARY。
- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:800-824`：RECALL 同时定义为 Search 返回“或”Context 入选。

**影响**

Usage 统计与 Loadout 展示会不稳定，N04 的测试无法确定正确期望。

**最小修正方案**

- Usage 模块独占 upsert；`asset_search` 每次对实际返回的每个 Asset 增加一次 RECALL，Context 入选不再额外增加。
- `asset_read` 成功返回当前文件后增加 READ；不存在 Task 时拒绝写 Usage，不自动创建孤儿 Task。
- `asset_mark_used` 把 USED 设为 1，重复调用保持 1；RECALL/READ 才累计。
- 模式统一为 DIRECT/ON_DEMAND；数组位置就是顺序，删除冗余 `order`。
- `schemaVersion` 保留；Loadout 由服务端校验后整体覆盖，只允许 RUNNING Task 更新，进入 COMPLETED/CANCELLED 后不再修改。

**为什么足够**

仍是一张 Task 表、一段 JSON 和一张 Usage 表，没有子表、Patch 协议、CAS 或事件流。

#### P1-04：解析失败时保留旧索引，会让 Codex 继续命中已失效内容

**问题描述**

增量规则明确写“解析失败不删除旧索引”。这让 SQLite 在 Markdown 已改变或 Frontmatter 已失效后继续返回旧正文，与“Markdown 是当前正式事实”冲突。FTS5 `trigram` 在目标 `better-sqlite3` 构建中的可用性和中文短词行为也尚未验证。

**具体失败场景**

用户修改正式 Asset 时写错 YAML；Search 继续返回旧摘要和旧正文片段，Read 却读取当前无效文件，Search/Read 不一致。文件监听失败时，MCP 仍无提示地使用陈旧索引。

**证据**

- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:553-589`：Catalog/FTS 和解析失败规则。
- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:1036-1070`：启动、监听与手工重建职责。
- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:1060`：解析失败明确保留旧索引。
- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:1091-1099`：故障表只说展示错误，未定义 Search 的陈旧行为。

**影响**

当前 Markdown 与搜索结果不一致，用户会基于已经撤回或损坏的旧知识工作。

**最小修正方案**

- 单 Asset 解析失败、未知类型、路径/Frontmatter 冲突或重复 ID 时，相关 Asset 的 Catalog/FTS 资格立即失效；文件不删除，只进入诊断列表。
- 启动全量扫描完成前 `/mcp` readiness 为 NOT_READY；索引 Schema/Repository 变化时标 `rebuildRequired`。
- watcher 失败时把状态标为 DEGRADED，并在 Search 响应附 warning；不谎称索引新鲜。
- `asset_read` 每次从当前白名单路径读取并校验 ID/Hash，不从 FTS body 返回全文。
- N02 前用目标 `better-sqlite3` 版本做内存数据库 Spike，验证 FTS5、`trigram`、中文 1/2/3 字查询、英文和代码符号；失败只调整 tokenizer/查询，不引入 Elasticsearch 或向量库。

**为什么足够**

只改变错误时的资格和状态，不增加第二套索引或恢复平台。

#### P1-05：人工整理按旧对象逐条复制，审核规模仍未收敛

**问题描述**

迁移设计要求每个 Version、Candidate 和候选 Document 各自出现一次，每条内嵌完整原文，即使重复也分别展示。当前只读盘点已经有 88 个 Version、5 个 Candidate、51 个 docs Markdown；其中 docs 又包含 CURRENT/FROZEN/HISTORICAL/EVIDENCE/GENERATED 等不同生命周期。该设计把“当前知识判断”重新变成了旧对象历史审阅。

**具体失败场景**

- 同一 MemoryItem 的多个互补 Version、历史 Version、Candidate 和审计文档重复表达同一知识，用户反复作相同决定。
- 单一 Markdown 长到无法可靠审阅，PENDING 永远难以归零。
- “旧项目和个人文档”没有根目录 allowlist，M00 无法证明盘点完整，也可能扩大成扫描整个主目录。
- 一个源 Version 需要拆成多个新知识时，Inventory 只有单个“对应审核编号”，无法表达覆盖关系。

**证据**

- `项目文档/设计方案/02-旧知识人工整理方案-修订版2.1.md:52-87`：所有 Version 单独列出，并加入候选 Document/Skill。
- `项目文档/设计方案/02-旧知识人工整理方案-修订版2.1.md:113-151`：三个主要文件和单一审核文档。
- `项目文档/设计方案/02-旧知识人工整理方案-修订版2.1.md:173-221`：每条完整原文、重复仍分别展示。
- `项目文档/设计方案/02-旧知识人工整理方案-修订版2.1.md:537-567`：M00/M01 为每个源项分配一个 REV 并写入一个完整文档。
- `/Users/hemu/Desktop/github/obsidian-notes/AGENTS.md:5-13`：当前 Canonical、Candidate、Generated、docs、tools 的真实目录职责。
- `/Users/hemu/Desktop/github/obsidian-notes/docs/DOCUMENT-LIFECYCLE.md:3-24`：docs 包含多种生命周期，Generated 和 Evidence 不等于当前知识。
- `/Users/hemu/Desktop/github/obsidian-notes/Memory/xm-ai-job/mem_33704096e119b2f6c4678e86/item.md:1-10`：Item 主要是主题容器。
- `/Users/hemu/Desktop/github/obsidian-notes/Memory/xm-ai-job/mem_33704096e119b2f6c4678e86/versions/mv_fund_architecture_20260816.md:1-65`：知识正文实际位于 Version。

**影响**

人工整理任务很可能无法完成，并重新携带旧系统对象复杂度。

**最小修正方案**

- Inventory 全量覆盖“源文件”，Review 审核“当前知识单元”；二者不要一一绑定。
- 每个 inventory source 记录 `disposition` 和 `reviewIds[]`；每个 review item 记录完整 `sourceRefs[]`。允许多源合一、一源拆多、精确重复只展示一次。
- 先按 Workspace + 主题聚类，再做 exact-hash 去重和语义近重复提示；冲突内容必须并列展示差异，不能静默合并。
- Review 条目展示最少必要信息和拟保留的完整当前内容；旧原文保留为可点击源路径，不在每个重复条目里复制全文。
- `v4-knowledge-review.md` 作为总索引与统计，实际审核按 10～20 条或固定字符预算拆到 `review-batches/`；这只是文件分批，不是新领域模型。
- 外部“项目/个人文档”必须由用户提供显式根目录 allowlist；未提供时标 UNKNOWN，不扫描整个主目录。

**为什么足够**

临时 Inventory 已经承担遗漏对账；Review 只需让人判断知识，不需要恢复 Version/Review/Relation 模型。

#### P1-06：HTTP MCP 方向可行，但服务生命周期和 Adapter 边界未冻结

**问题描述**

主设计称一个 Node 常驻服务同时提供 `/mcp`、`/api`、静态 Hub 和监听，但直到 N08 才要求启动/停止说明。服务未启动、配置时是否 required、端口占用、服务重启后的已有会话重连均未定义。STDIO Adapter 又可转发到 `/mcp`“或内部 API”，后者会诱发第二套工具映射。

**具体失败场景**

- Codex 启动时 Node 未运行，MCP 初始化失败并产生不确定的普通任务行为。
- Node 重启后当前 Codex turn 继续持有失效 session，用户不知道要刷新 MCP 还是重开客户端。
- Adapter 走内部 REST 后重复实现 tool list、参数映射、错误码和 Usage 语义。
- 动态端口变化后 Codex config 指向旧地址。

**证据**

- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:172-189`：单进程形态与 Adapter 两种上游目标。
- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:828-903`：MCP/Adapter 缺少进程和重连契约。
- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:1089-1099`：只写“服务不可用不阻断”，未说明如何由配置保证。
- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:1167-1182,1291-1298`：N00 做 ping，启动停止说明却留到 N08。
- 当前 `codex-cli 0.147.0` 的 `codex mcp add --help` 明确提供 `--url`，描述为 Streamable HTTP server。
- 官方文档明确列出 STDIO 与 Streamable HTTP，并提供 `url = "http://localhost:3000/mcp"`、`required`、startup/tool timeout 配置：[OpenAI Codex MCP documentation](https://developers.openai.com/codex/mcp)。

**影响**

HTTP MCP 不是 NO-GO，但在真实日常运行前会有明确返工和可用性风险。

**最小修正方案**

- 固定 `127.0.0.1` 和一个配置端口；端口占用即清楚失败，不实现端口管理服务。
- 提供一个前台 `serve` 命令和 start/stop/status 文档；是否用 macOS LaunchAgent 后续再定，不先造自定义 daemon。
- Codex MCP 配置明确 `required=false`，服务不可用时普通 Codex 仍可启动；知识工具显示 unavailable。
- Adapter 只能桥接 STDIO MCP ↔ 同一 `/mcp`，不能调用内部业务 REST。
- 服务运行时只允许一个写 SQLite 的 Node 进程；第二实例因端口占用失败。
- 把断线、同会话重连和多窗口纳入 N00 Spike，结果写进设计后再决定是否实现 Adapter。

**为什么足够**

复用 Codex 配置、OS 进程和同一 HTTP MCP，不需要额外守护进程、服务发现或认证平台。

#### P1-07：Hub 页面范围合理，但 System Status 有缺项和不可观测字段

**问题描述**

Hub 页面保持只读，但 System Status 漏掉冻结要求的“索引是否需要重建”和“Workspace 识别异常”。同一 Node 服务在停止时无法由自己托管的页面显示“Node 服务 down”；它也不能仅凭自身证明 Codex 已连接，STDIO Adapter 没有心跳时更无法显示运行状态。

**具体失败场景**

- watcher 或 Schema 变化后索引需要重建，用户只看到最后索引时间，无法判断是否可相信 Search。
- Workspace path 重叠/未知时，页面没有直接诊断。
- 页面显示“HTTP MCP 正常”被误读为“Codex 当前连接正常”，实际只证明 endpoint ready。
- 为显示 Adapter 状态而反向新增心跳表或守护进程。

**证据**

- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:911-989`：Asset/Task/Usage 页面均可由现有数据获得。
- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:991-1007`：System Status 当前字段。
- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:1036-1070`：索引已有启动、监听和 rebuild 概念，但未形成状态 DTO。

**影响**

Hub 无法完整承担固定的排错目标，或为了填页面字段而增加不必要后端状态。

**最小修正方案**

把 System Status 定义为计算型 DTO，不建新表：

- `service`: version、uptime、ready；页面请求失败本身表示服务 down。
- `mcpEndpoint`: ready/not-ready，只表示 endpoint，不声称 Codex client connected。
- `repository`: path、readable、formal/inbox counts、Git dirty。
- `index`: READY/DEGRADED/REBUILD_REQUIRED、reason、catalog/fts counts、last successful full scan、watcher status。
- `diagnostics`: parse failures、duplicate IDs、path/frontmatter conflicts、unknown types、workspace config/path-match errors。
- Adapter 未实现时显示 `NOT_CONFIGURED`；没有可证心跳时不显示 `RUNNING`。

**为什么足够**

全部可由当前进程、Scanner、配置、SQLite 和 Git CLI 即时计算，不需要 Dashboard 数据仓库或新领域模型。

#### P1-08：阶段依赖有直接冲突，多个任务大于一个独立对话

**问题描述**

主设计要求 N08 完成后“M02 之后任务可以启动”，迁移设计却让 M02 只依赖 M01、M03 依赖 N01/N02/N07。N00 同时创建整个 workspace、Hono、Vue 空壳和 HTTP Spike；N02 同时做全量/增量索引、Search/Read 和 Golden Query；N06 一次实现五个 Hub 页面。

**具体失败场景**

- 团队无法判断 M02 能否与新系统实现并行。
- MCP Spike 被前端骨架拖慢，失去“先证伪传输”的价值。
- N02/N06 在一个对话中产生过大 diff 和模糊验收。
- M01/M02 单个超长审核任务无法完成，后续状态长期停在 IN_PROGRESS。

**证据**

- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:1167-1298`：N00～N08 当前任务粒度。
- `项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:1298-1303`：主设计对迁移 M02 的依赖。
- `项目文档/设计方案/02-旧知识人工整理方案-修订版2.1.md:537-639`：M00～M05 当前依赖。

**影响**

会产生阶段返工并降低每个 Codex 对话的可验证性。

**最小修正方案**

- N00a 只做 HTTP MCP ping/restart/multi-client Spike；N00b 再建正式 workspace/server/hub 骨架。
- N02a 做可重建 Catalog/FTS；N02b 做 Search/Read + Golden Query；N02c 再做 watcher。
- 把最小 Task correlation/Hook 放到正式 MCP Usage 集成前。
- N04 拆为 Loadout、Usage 两个任务；N06 按“只读 API、Asset 页面、Task/Usage 页面、Status”拆分。
- M00 只做 Inventory；M01 按 Workspace/主题生成 batch；M02 按 batch 人审；M03/M04 也按 batch 生成和确认。
- 统一依赖：M00/M01/M02 可在 Asset 文件契约冻结后并行进行；M03 依赖 IdGenerator + Inbox 写入契约；M04 搜索验收才依赖 Catalog/Search；M05 依赖新 MCP 已稳定。

**为什么足够**

只是重排和拆小既有任务，不新增产品能力。

### 4.3 P2 Findings

#### P2-01：`usage_id` 和 Loadout `usageId` 没有独立业务作用

`UNIQUE(task_id, asset_id)` 已经唯一标识 Usage；所有查询都天然从 Task/Asset 出发。额外 `usg_...` 让 IdGenerator、JSON 和 Hub 多维护一个可推导标识。证据：`项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:613-630,738-780,969-987`。建议删除 `usage_id`，以 `(task_id, asset_id)` 为主键；这也回答“是否存在没有必要生成独立 ID 的对象”。

#### P2-02：Loadout JSON 同时保存数组顺序、`order` 和派生 `result`

数组本身已有顺序，`assetCount`、`injectedAssetCount`、`injectedCharacters` 都能从 items 派生。证据：`项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:740-770`。建议保留 `schemaVersion`、limits 和最小 Asset items，Hub 在读取时派生汇总；若后续证明列表 SQL 必须按这些值过滤，再增加普通列，不先加。

#### P2-03：目录 Asset 的 Hash 算法属于未来需求

当前明确只有单文件 Asset，却提前冻结递归、路径排序和 symlink 行为。证据：`项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:468-478,1397-1400`。建议将目录算法整体移到 Deferred，只保留“第一版不接受目录 Asset”；不影响三种 Asset 类型。

## 5. Ablation Matrix

| 能力 | 解决的具体问题 | 删除后的结果 | 现有机制能否替代 | 本期必需 | 结论 |
|---|---|---|---|---:|---|
| Snowflake ID | 为文件、Task 提供稳定且可读的系统 ID | 文件改名后仍可凭 ID 识别，但若完全无 ID 将难以稳定引用 | 路径可部分替代但冻结决策已选定 Snowflake | 是 | **KEEP**；补最小单机规则，不建 ID 服务 |
| Asset 三种类型 | 区分短知识、长文档和方法型内容的展示/装配 | 所有内容被同一种注入策略处理 | 一个枚举足够，不需三套领域模块 | 是 | **KEEP** |
| `assets/` / `inbox/` | 阻止候选默认污染正式检索 | Codex 候选可直接进入后续任务 | 数据库状态可替代但会违背冻结 Human-First | 是 | **KEEP** |
| Workspace | 防止项目知识串入其他项目 | 可能应用错误约束 | 仅依靠标题/标签不能形成硬过滤 | 是 | **KEEP**；收紧可信绑定 |
| Content Hash | 检测当前文件变化和移动前后字节一致 | 无法快速判断索引/候选是否变化 | Git 不能覆盖未提交工作树 | 是 | **KEEP** |
| SQLite Asset Catalog | 快速列出元数据并支撑 Hub | 每次请求都需全量扫描文件 | 内存扫描可替代但不利于稳定查询 | 是 | **KEEP**；保持可重建 |
| SQLite FTS | 提供正文全文检索和 snippet/score | 只能标题/摘要线性匹配 | 线性扫描可作测试基线，不能满足既定全文搜索体验 | 是 | **KEEP**；先验证 tokenizer |
| Task Loadout 固定字段 | 高频查询 Task、Workspace、状态和时间 | Hub/Hook 只能解析整段 JSON | JSON 可替代但会让常用过滤变差 | 是 | **SIMPLIFY**；保留固定列并加 source correlation |
| `loadout_json` | 容纳易变的装配顺序、模式、原因和预算 | 需要多个子表或频繁改 Schema | 多表不是更简单 | 是 | **SIMPLIFY**；最小 JSON + schemaVersion |
| `task_asset_usage` | 独立保存每 Task/Asset 的三态使用情况 | 丢失 Usage 页面和 mark-used 结果，但不影响知识 | Loadout JSON 不应承担计数 | 是 | **SIMPLIFY**；复合主键，无 usage_id |
| RECALL / READ / USED | 区分被展示、被完整读取、被明确采用 | 无法观察检索是否真正被使用 | 单一 used 标志不能替代前两层 | 是 | **KEEP**；Recall/Read 累计，Used 幂等 0/1 |
| HTTP MCP | 让 Codex 直接调用同一常驻服务 | 只能经每会话子进程访问 | STDIO 可替代，但 Hub 已需要 HTTP 服务 | 是 | **KEEP**；CONDITIONAL GO |
| 薄 STDIO Adapter | 在特定 Codex 客户端 HTTP 不稳定时兼容 | 若 HTTP Spike 通过则无损；失败环境没有入口 | 直接 HTTP 是首选替代 | 条件必需 | **DEFER**；KEEP AS FALLBACK |
| Vue Hub | 让个人查看 Asset、Loadout、Usage 和故障 | 仍可用 MCP/编辑器，但缺固定只读产品目标 | CLI 可部分替代，不满足冻结 UI 目标 | 是 | **KEEP**；不能反向造模型 |
| System Status | 定位解析、重复、索引和 Workspace 问题 | 故障只能查日志 | 日志不够直观；计算 DTO 足够 | 是 | **SIMPLIFY** |
| 旧知识人工审核文档 | 让用户决定当前保留内容 | Codex 会替人自动迁入或旧知识无法进入新系统 | 直接迁移不符合 Human-First | 是 | **SIMPLIFY**；总索引 + 小批次、源覆盖映射 |
| KEEP/MERGE/REWRITE/DROP | 覆盖保留、合并、修改和放弃 | 需要自由文本且难以对账 | 四态已覆盖第一版实际选择 | 是 | **KEEP** |
| Git | 记录人工 Markdown 的普通历史和恢复 | 只能靠文件备份，缺 Diff/回退 | 应用内 Revision 会显著增复杂度 | 是 | **KEEP**；提交由用户决定 |

## 6. Data Model Review

### 6.1 Asset

**稳定身份**

- Asset 身份只由 Frontmatter `id` 决定，文件移动或改名不改变身份；该方向正确（`项目文档/设计方案/01-知识运行时设计方案-修订版2.1.md:442-456`）。
- `file_path` 是 Catalog 的当前定位，不是身份。Scanner 看到同 ID 新路径时应更新定位，而不是创建新 Asset。
- 单文件 Asset 是唯一 MVP 形态；目录必须在 Schema 层明确拒绝，而不是半支持。

**最小 Frontmatter**

`id / type / scope / workspace? / title / summary` 足够。MEMORY、DOCUMENT、SKILL 当前不需要三套 Schema；类型只影响默认装配和展示。正文必须是合法 UTF-8 Markdown，Frontmatter Schema 严格拒绝未知枚举值，但不需要拒绝普通额外 Markdown 内容。

**scope 与 workspace**

两者不完全重复：`scope` 表达 GLOBAL/WORKSPACE 分类，`workspace` 给出 WORKSPACE 的具体值。既然目录也表达 scope，必须把三者一致性作为索引不变量，而不是任选一个为准：

```text
GLOBAL    => workspace absent && path under assets/global/<type>/
WORKSPACE => workspace exists in config
             && path under assets/workspaces/<same-workspace>/<type>/
```

不满足时文件保留但不进入搜索。未知 Workspace、未知 type、无 Frontmatter、重复 ID、目录型 Asset、symlink 均进入 diagnostics。这样不会引入状态字段，也不会错误覆盖正式 Markdown。

**Global 与 Workspace 资格**

Search/Read/Mark Used 共用一个资格函数；GLOBAL 可进入任何已识别 Task，WORKSPACE 只能进入同名 Task。无法识别 Workspace 时只允许 GLOBAL。禁止在 Read 阶段因为“已有 assetId”而绕过资格。

### 6.2 IdGenerator

建议在 N01 前冻结以下最小协议：

```text
business id = <prefix>_<snowflake-decimal>
prefix      = ast | tsk
snowflake   = 41-bit timestamp | 10-bit worker | 12-bit sequence
worker      = 0 (single local Node service)
sequence    = 0..4095 per millisecond; overflow waits for next millisecond
internal    = bigint
external    = string/TEXT only
```

若按本报告删除独立 `usage_id`，第一版 `IdPrefix` 只需 `ast | tsk`；`usg` 不应为了“格式统一”而保留一个无业务用途的 ID。若文档最终坚持 usage_id，则统一用 `usg_`，但这不是推荐方案。

Epoch 必须写为一个不可变 UTC 时间常量。运行中时间回退立即拒绝生成；启动时比较当前时间和从现有 Asset/Task ID 可解析出的最大时间水位。所有 JSON 序列化之前必须已经转成 string，禁止 `JSON.stringify(bigint)`。`validate` 同时校验前缀、下划线、纯十进制、位宽和时间范围；业务代码不得拼接 prefix。

### 6.3 Task Loadout

**普通列**

建议保留并冻结：

```text
task_id
source_session_id
source_turn_id
workspace              # nullable; NULL means GLOBAL-only task
request
status
loadout_json
created_at
updated_at
```

`UNIQUE(source_session_id, source_turn_id)` 用于 Hook 幂等关联。`request` 保存完整用户原文，Hub 列表摘要在应用层截取；无需再加 `request_summary`。`asset_count` 与 `estimated_context_characters` 当前只展示、不按 SQL 过滤，先从 JSON 派生，不加普通列。

**状态**

只需要：

```text
RUNNING -> COMPLETED
RUNNING -> CANCELLED
```

终态不可回到 RUNNING，不需要 FAILED、RETRYING、ARCHIVED。Hook 或服务故障不应阻断 Codex；可能遗留 RUNNING，由 SessionEnd 或启动清理标为 CANCELLED 即可。

**并发与更新**

UserPromptSubmit 对 source pair 做一次事务型 upsert；Loadout 在 RUNNING 内由服务端整体替换 JSON，不支持客户端 JSON Patch。Stop/Interrupt 只更新 status/updated_at。单进程同步 SQLite 写入足以串行化，事务覆盖 Task + Usage 的相关写入，无需版本列或分布式锁。

### 6.4 `loadout_json`

`schemaVersion` 必须保留，否则 Hub 和服务无法区分未来兼容结构。推荐最小结构：

```json
{
  "schemaVersion": 1,
  "limits": {
    "maxInjectedCharacters": 3000,
    "maxAssets": 8
  },
  "assets": [
    {
      "assetId": "ast_2034512345678901248",
      "mode": "DIRECT",
      "reason": "标题和摘要与当前请求直接相关",
      "estimatedCharacters": 96
    },
    {
      "assetId": "ast_2034512345678901255",
      "mode": "ON_DEMAND",
      "reason": "长文档按需读取",
      "estimatedCharacters": 0
    }
  ]
}
```

数组位置就是装配顺序。不要保存 Asset 完整 Markdown、Usage 次数、usageId、重复 title/summary 或可派生 result。Asset 删除后历史 Loadout 保留 assetId，并在 Hub 显示 `Asset missing`；不复制正文来维持历史展示。

### 6.5 Usage

推荐模型：

```sql
CREATE TABLE task_asset_usage (
    task_id      TEXT NOT NULL,
    asset_id     TEXT NOT NULL,
    recall_count INTEGER NOT NULL DEFAULT 0 CHECK (recall_count >= 0),
    read_count   INTEGER NOT NULL DEFAULT 0 CHECK (read_count >= 0),
    used_count   INTEGER NOT NULL DEFAULT 0 CHECK (used_count IN (0, 1)),
    created_at   TEXT NOT NULL,
    updated_at   TEXT NOT NULL,
    PRIMARY KEY (task_id, asset_id),
    FOREIGN KEY (task_id) REFERENCES task_loadout(task_id) ON DELETE CASCADE
);
```

- RECALL：每次 `asset_search` 实际返回该 Asset 时 `+1`。
- READ：`asset_read` 完整、成功返回当前文件时 `+1`。
- USED：只有 `asset_mark_used` 显式调用时设为 1；重复调用幂等。
- Task 不存在时返回 `TASK_NOT_FOUND`，不创建孤儿 Usage。
- 不对可重建 Catalog 建外键；Asset 删除后 Usage 行保留，Hub 显示 ID + missing。
- SQLite 丢失只丢运行统计，不影响正式 Asset 或索引重建。

这仍然只有 RECALL/READ/USED 三种语义，不是 Usage Event 平台。

### 6.6 SQLite

一个 `codex-memory.sqlite` 足够。逻辑上分两类表，不应拆成多个数据库：

- 可重建：`asset_catalog`、`asset_fts`，以及非持久 diagnostics 的当前扫描快照。
- 可丢失运行数据：`task_loadout`、`task_asset_usage`。

最低运行设置：`PRAGMA foreign_keys=ON`；一个 Node 进程持有写连接；WAL 允许 Hub 读与 Usage 写并行；设置有限 `busy_timeout`；所有 Catalog/FTS 同步更新在一个事务内。无需连接池、读写分离或外部锁服务。

职责边界：

- 启动扫描：在 MCP ready 前建立一次一致的当前索引。
- 文件监听：只做后续增量；失败时标 DEGRADED。
- 手工 rebuild：只重建 Catalog/FTS，不清 Task/Usage，不移动 Markdown。
- Scanner 异常：相关 Asset fail closed，其他 Asset 可用。
- 整体索引陈旧：Search 返回明确状态/warning；不能静默宣称是当前结果。

### 6.7 Content Hash

单文件 `SHA-256(文件实际字节)` 已经满足第一版全部用途。它会覆盖 Frontmatter 和正文，换行、Unicode 或 YAML 顺序变化都会改变 Hash，这是已冻结的简单行为，不需要 canonicalization。移动/改名不改变文件字节，因此不改变 content hash 或 Asset ID。

Content Hash 不是版本号、确认记录或跨系统等价证明。目录 Asset 尚未支持时不保留目录算法。Usage 是否记录读取时 Hash 是可选项；当前 MVP 可以不记录，避免为了历史精确性扩大表结构。

## 7. MCP and Runtime Review

### 7.1 一个 Node 服务同时提供 Hub REST 与 HTTP MCP

**合理。** 两者共享 Asset Service、Context、Usage、Scanner 和一个 SQLite，分进程只会增加生命周期和一致性成本。路由层保持分离即可：`/mcp` 处理 MCP；`/api/*` 只读供同源 Hub；`/internal/*` 只供本地 Hook。Vue 静态资源由同进程托管也符合个人本地边界。

### 7.2 当前 Codex 对 Streamable HTTP 的支持

**官方文档事实**：OpenAI Codex MCP 文档明确列出 STDIO 和 Streamable HTTP 两种 server feature，支持用 URL 配置，并说明本地 Codex clients 共享 host 上的 MCP 配置：[OpenAI Codex MCP documentation](https://developers.openai.com/codex/mcp)。

**本地事实**：本机 `codex-cli 0.147.0` 的 `codex mcp add --help` 明确显示 `--url <URL>`，描述为“Use --url for a streamable HTTP server”。当前旧 Engineering Memory 仍通过 STDIO 注册（`/Users/hemu/.codex/config.toml:108-114`），其 server 是逐行 JSON-RPC STDIO 循环（`/Users/hemu/.codex/engineering-memory/mcp_server.py:397-460`）。旧系统使用 STDIO 只证明旧链路可用，不证明新系统必须继续 STDIO。

**结论**：协议能力已得到文档和 CLI 级验证；本项目具体 Node SDK 实现、当前 Desktop build、断线重连和多窗口仍须 Spike。

### 7.3 启动、停止与重连边界

- 服务未启动：Codex MCP 配置应为 `required=false`；MCP 工具不可用，但普通任务不失败。Hub URL 同时不可访问。
- 服务启动：使用固定 `127.0.0.1:<port>`；提供前台 `serve`，不要求额外 daemon。
- 服务停止：关闭 HTTP listener、watcher 和 SQLite；不修改 Asset 文件。
- 服务重启后现有 Codex 会话能否自动恢复：**UNKNOWN**。官方文档要求新增/修改 MCP 配置后 Restart client，但没有承诺已配置 HTTP server 的运行时重启行为。
- 若需要手工 `/mcp` refresh、Restart extension/app 或重开会话，必须由 Spike 记录真实行为后写入运行手册。

### 7.4 多窗口共享

**推断**：所有窗口连接同一个固定端口的 Node 服务，因此共享同一个 Task Loadout/Usage SQLite。Task 以 `source_session_id + source_turn_id` 唯一关联，不会因多个客户端而混在一起。单 Node 写进程和 SQLite 事务足以处理并发；不需要每窗口数据库或锁服务。

### 7.5 localhost、Host、Origin、端口与认证

- 只绑定 IPv4 `127.0.0.1`，不要绑定 `0.0.0.0`。
- Codex 配置使用稳定的 `http://127.0.0.1:<fixed-port>/mcp`，不要依赖动态端口。
- Host 只接受配置的 `127.0.0.1:<port>`；不做通配。
- 原生 MCP 请求可无 Origin；若有 Origin，只接受同源 Hub `http://127.0.0.1:<port>`，拒绝外部网页 Origin。
- 不启用通配 CORS；Hub 与 API 同源。
- 在“个人本机、只信任本机用户进程”的当前威胁模型下，无 Bearer token 也可作为 MVP。若未来允许局域网监听或不信任本地进程，再启用官方已支持的 bearer token；当前不需要认证服务。
- 端口冲突直接启动失败并打印占用端口；不实现端口协调器。

### 7.6 MCP 工具的读写语义

业务内容边界：

- `task_loadout_get/list`：纯只读。
- `asset_search/read`：不修改 Asset，但会写非关键 RECALL/READ Usage，因此在 MCP annotation 上不是严格 read-only，也不是幂等。
- `asset_mark_used`：只把非关键 `used_count` 设为 1，不改 Asset；应是 non-destructive、idempotent write。

旧 MCP 已因自动 Usage 把 Search/Read 标为 `readOnlyHint: false`（`/Users/hemu/.codex/engineering-memory/mcp_server.py:31-83,306-350`），这反而说明新设计不能一边自动计数、一边宣称工具完全只读。建议 annotation：

| 工具 | readOnlyHint | destructiveHint | idempotentHint |
|---|---:|---:|---:|
| asset_search | false | false | false |
| asset_read | false | false | false |
| asset_mark_used | false | false | true |
| task_loadout_get | true | false | true |
| task_loadout_list | true | false | true |

### 7.7 薄 STDIO Adapter

结论：**KEEP AS FALLBACK**，但在 HTTP Spike 失败前不实现。

Adapter 只做：STDIO MCP initialize/list/call/cancel ↔ 上游 Streamable HTTP `/mcp` 的协议桥接、超时与错误转发。它不读取 Asset、不连接 SQLite、不生成 ID、不认识 Workspace、不解释 Usage、不调用业务 `/internal` REST。若 `/mcp` 服务本身坏了，Adapter 不应掩盖错误。

### 7.8 最小兼容性实验

实现正式业务前只建一个 `ping` tool，完成以下矩阵：

1. 记录 Codex CLI/Desktop 版本、MCP SDK 版本、配置和固定 URL。
2. CLI 和当前 Desktop 分别完成 initialize、tools/list、ping。
3. Codex 先启动、服务后启动，观察是否能在不重开对话时恢复。
4. 保持同一对话，停止并重启 Node，再调用 ping。
5. 两个 Codex 窗口并发 ping，确认 session 不互相覆盖。
6. 服务未启动且 `required=false` 时，确认普通 Codex 任务仍可用。
7. 验证 Host/Origin：合法本地请求通过，错误 Host/外部 Origin 被拒绝。
8. 若任一目标客户端的直接 HTTP 失败，再实现同一 ping 的薄 STDIO Adapter 并重复测试。

Spike 只回答兼容性，不建立 Catalog、Task、Usage 或 Hub。

### 7.9 完全舍弃 MCP 的代价

CLI/curl 可以证明后端 Search/Read，但 Codex 不再获得结构化工具 Schema、工具发现、标准调用结果、Task 关联和显式 `asset_mark_used`。用户必须手工复制命令与结果，无法满足“Codex 在具体任务中搜索、读取和使用知识”的首选体验。因此不应删除 MCP。

### 7.10 MCP Final Decision

```text
HTTP MCP:       CONDITIONAL GO
STDIO Adapter:  KEEP AS FALLBACK
```

当前 UNKNOWN：Desktop 对本项目服务器的实测、运行中服务重启后的连接恢复、Node MCP SDK/Hono 的具体集成方式、合法 Origin/Host 的实际请求形态。它们都由上述最小 Spike 解决，不应继续靠设计猜测。

## 8. Hub MVP Review

### 8.1 页面范围

Asset Library、Asset Detail、Task Loadout、Usage、System Status 五页足够，且仍是只读 MVP。没有在线编辑、移动、确认、Git、标签或 Dashboard，不应删除固定要求中的 Document、Usage 或 Hub。

### 8.2 数据来源

| 页面/字段 | 数据来源 | 结论 |
|---|---|---|
| Asset ID/title/type/scope/workspace/summary/path/mtime/hash | `asset_catalog` | 已有 |
| 搜索 snippet/score | `asset_fts` 查询结果 | 已有；需明确分数方向/展示文案 |
| Inbox 列表 | Scanner 对 `inbox/` 的只读即时扫描 | 不进入默认 FTS；无需 Inbox 表 |
| 渲染/原始 Markdown/Frontmatter | 按 Catalog 白名单路径读取当前文件 | 已有；必须重新校验 ID/Hash |
| Asset Usage 汇总/最近 Task | `task_asset_usage` join `task_loadout` | 已有；Asset missing 时降级显示 ID |
| Task 固定字段 | `task_loadout` 普通列 | 已有 |
| Task assets/mode/reason/order/字符数 | 解析 `loadout_json` | 已有；数组位置为 order |
| Usage 按 Task/Asset/Workspace | Usage join Task | 已有；不需要 Workspace 冗余列 |
| System Status | 当前进程 + Scanner diagnostics + SQLite + Git CLI | 需补 DTO 契约，不建新表 |

### 8.3 应补的排错信息

- `indexState`、`rebuildRequired`、reason。
- 最后一次成功全量扫描时间，而不只是单行最大 `indexed_at`。
- Workspace 配置重复、路径重叠、cwd 无匹配、目录/Frontmatter workspace 冲突。
- 服务 version/uptime/readiness。
- FTS tokenizer/Schema version，便于解释索引为何要求 rebuild。

这些字段直接影响排错；不需要趋势图、评分、排行榜、用户权限或连接历史。

### 8.4 应删除或改名的状态

- “Node 服务状态”改成页面可取得的 `service ready/uptime`；页面打不开就是 down。
- “HTTP MCP 状态”改成 endpoint readiness，不能声称 Codex 已连接。
- “STDIO Adapter 状态”只允许 NOT_CONFIGURED/CONFIGURED，除非以后真实增加心跳；不为页面新增心跳表。
- SQLite status 只说明 open/schema/pragmas，不在每次页面加载跑重型 integrity check。

结论：Hub MVP **范围合格，数据基本可得**；完成 P0 Workspace 契约、Task/Usage 和 Index Status 后再实现，不应先由页面倒推新后端模型。

### 9.4 去重与聚类流程

```text
显式根目录 inventory
  → 每个源文件路径 + bytes hash + 类别 + Workspace + read status
  → exact hash 去重
  → 按 Workspace + 主题聚类
  → 标记近重复、互补、冲突、可拆分内容
  → 形成当前知识 review item
  → source.reviewIds[] 与 review.sourceRefs[] 双向覆盖校验
```

Codex 应先聚类，但不能静默决定。Exact duplicate 可以只展示一次完整内容，列出所有来源；近重复和冲突必须把差异展示给用户。一个 Version 含多个独立判断时拆成多个 review item；多个 Version 表达同一判断时合成一个 review item。

### 9.5 单个审核条目的最少信息

- `REV-xxxx` 临时审核编号。
- Workspace、主题、建议 title/type/scope/summary。
- 所有 source path、source category、旧状态参考、hash。
- Codex 提炼出的“拟保留当前内容”完整草稿。
- exact duplicate、互补和冲突说明。
- Codex 建议及理由。
- 用户决定、merge group、rewrite 要求、补充说明。

无需把每份重复旧原文复制进同一文件；源文件在整理期间保持不动，可按路径打开。

### 9.6 KEEP / MERGE / REWRITE / DROP

四种决定足够：

- KEEP：当前草稿可直接生成一个 Inbox Asset。
- MERGE：多个 review item 汇入一个 merge group；必须列全来源 REV ID，合并草稿再次由用户检查。
- REWRITE：保留用户改写要求原文，Codex 生成新的完整草稿，不把自动补充当事实。
- DROP：不生成 Asset；不建 Archive 或恢复状态。

拆分不是第五种决定：在审核前把一条源材料拆成多个 review item，用户分别使用四种决定即可。

### 9.7 分批审核

需要分批。建议 `v4-knowledge-review.md` 只做总索引、统计和 batch 链接，`review-batches/<workspace>-<nn>.md` 每批 10～20 个 review item 或固定字符预算。用户可在一个 Codex 对话完成一批；主索引只汇总决定，不复制全部正文。

这不会形成迁移平台：batch 是普通临时 Markdown，最终不进入 Asset Core。

### 9.8 Inbox 生成与最终对账

生成前检查：Review item 非 PENDING；type/scope/workspace/title 明确；MERGE 组闭合；REWRITE 有要求。每个目标 Asset 重新生成 `ast_` ID，写入正确 `inbox/` 路径，不携带旧 ID 或审核编号。

Generation report 至少记录：

- review item/merge group → 新 Asset ID + inbox path；
- DROP；
- 生成失败；
- Frontmatter/Hash/path 校验；
- 最终进入 assets 或退回 inbox 的结果。

完成对账应同时满足：

1. 每个 inventory source 都有 disposition 和 reviewIds，读取失败显式列出。
2. 所有 review item 的 PENDING 为 0，MERGE group 闭合。
3. KEEP/MERGE/REWRITE 均有恰好一个或用户明确要求的多个 Inbox 输出。
4. 所有 Inbox 输出已由用户最终检查；确认的文件进入 assets。
5. 新 Catalog/FTS 可命中关键知识，其他 Workspace 不串入。

不需要 ImportAttestation、Shadow、回滚、双轨或旧 Usage。
