## 2. 根因、差异分类与最小算法

修复前 `calculateDifference` 遍历旧 Catalog 行，通过 `sameIdAsset ?? assetsByPath.get(row.filePath)` 寻找新 Asset。删除 A 再把 B 移到 A 路径后，旧 A 经路径匹配 B，旧 B 经 ID 匹配 B，得到 `changed=[B,B]`。`consumedAssetIds` 只影响 added，不能阻止 changed 重复写入。Scanner 生成的 Snapshot 合法，错误产生在差异计算。

原有消费者 `apps/server/src/asset/catalog.ts:112` 已在单一 SQLite 事务内先删除全部受影响旧行，再插入新行；`:264` 按旧 rowid 删除 FTS/Catalog，`:278` 普通 INSERT Catalog 后以 lastInsertRowid 插入 FTS。因此无需改写事务、约束或状态体系，只需修正差异集合。

本轮生产修改仅在 `apps/server/src/asset/catalog.ts:354`：

1. 构造新 Snapshot 与旧 Catalog 的 ID 映射。
2. 遍历新 Snapshot 的唯一 ID：无旧身份则 added；同 ID 且现有 `sameCatalogValues` 全字段相等则 unchanged；否则 changed，并记录该 ID 的旧 changedRow。
3. 独立遍历旧行：新 Snapshot 已没有该 ID 时，按原路径诊断规则分类为 invalidatedRows 或 removedRows；不再以被其他身份占据的旧路径认领新 Asset。
4. 复用现有事务，先删除 removed/invalidated/changed 的全部旧 FTS 和 Catalog 行，再对 changed/added 各新身份写入一次。两个删除分类与 changedRows 互斥；changed/added 互斥；unchanged 完全不写。

Scanner 仍负责完整 Snapshot 与重复 ID 全部排除，差异函数接收的是该合格集合；没有新增“重复 ID 取一个获胜者”的 Scanner 行为。复杂度保持按新旧集合线性处理，没有全库清空再重建。

| 分类 | 修复后的准确含义 | 与旧统计的关系 |
|---|---|---|
| added | 新 Snapshot 有、旧 Catalog 无的 Asset ID | 同路径换新 ID 现在记 added；旧算法把它计为 changed |
| changed | 新旧均有该 ID，但路径、Hash、类型、范围、Workspace、标题、摘要、大小或 mtime 等现有比较字段有变化 | 同 ID 移动仍是 changed，每个新身份一次 |
| unchanged | 同 ID 且现有比较字段全部相等 | 保留 rowid、indexed_at，完全不写 |
| invalidated | 新 Snapshot 无该旧 ID，且诊断命中它的旧路径 | 保留原诊断路径分类规则 |
| removed | 新 Snapshot 无该旧 ID，且无上述路径诊断 | 消失身份即使旧路径被另一身份复用，也计 removed |

因此，“同路径换新 ID”是 removed=1、added=1，“同 ID 移动”是 changed=1。该统计调整遵循本轮身份要求，不合并或转移历史。`CatalogSyncResult` 字段结构不变；当前生产调用方是 IndexManager，HTTP/MCP 没有返回这组同步统计。现有 `asset-index.test.ts:158` 的单个 replaced 统计断言相应改为完整五字段断言，其旧身份消失、路径正确、旧 FTS 消失及新 FTS 命中的原断言全部保留。

现有 `sameCatalogValues`、兼容导出、Schema 和一致性检查未清理。`IndexManager:207` 的完整 Snapshot gate、`:225` 的成功状态更新、`:231` 的真实失败处理均未改动；不完整扫描仍不应用删除，失败不伪报 READY。

## R5. U03 新 Finding：固定 node 的跨进程身份碰撞

当前调用点核对：主服务 `runtime.ts:115` 创建生成器用于 Task/Usage；独立 Hook `user-prompt-submit.ts:119` 自建生成器；Task/Usage ApplicationService 也有默认生成器。Schema 与 HTTP contracts 中只做 ID 验证，不生成身份。Task 的 `next("tsk")` 在 `task/service.ts:56` 的事务回调内（`repository.ts:220–265` IMMEDIATE）；Usage `service.ts:68` 先生成 `usg`，再进入 Repository 写事务。当前生产没有自动创建新 Asset 身份的调用；统一生成器仍负责 ast 格式。

**可达原因：** 锁定 snowflake.io 4.1.2、node=0、进程局部 sequence。SQLite 把写操作串行化并不共享 Snowflake 序列；多个进程第一次生成同毫秒 ID，仍可能得到相同值。不是同进程 Promise 压测问题。

正式 `packages/id-generator/test/multiprocess.test.ts` 用 8 个真实 Node 子进程，导入模块前固定 `Date.now=1900000000000`，依次生成 ast/tsk/usg。修复前每个前缀只有 1 个唯一值，断言 expected=8/actual=1，**0/1**（`u03-before.log`）。不改变该时序与断言，修复后 **1/1**；包全量 **5/5**，保留原格式、20,000 次本进程唯一性、JSON 字符串与时钟回退拒绝测试。

最小方案比较：

| 方案 | 判断 |
|---|---|
| 维持原样或只依赖 SQLite 串行 | 正式反例已证明不足；唯一约束只报错，不避免冲突 |
| 随机有限 worker ID | 仍有较小空间 worker 碰撞且引入节点语义，不采用 |
| 跨进程节点分配/持久化时钟水位 | 超出当前单机精简边界，不采用 |
| Task/Usage 各自加冲突重试 | 复制生成规则，仍需解决 ast 生成与多处路径，不采用 |
| 保留 Snowflake 并每 ID 组合 128 位随机量 | 采用 Node 内置 crypto，不改依赖/Schema/前缀/字符串校验，不新增分配平台 |

`packages/id-generator/src/index.ts:25–27`：先执行原 Snowflake（保留回退抛错），再生成 16 字节随机量，组合为 `(snowflake << 128) | nonce` 并输出十进制字符串。旧 ID 继续验证通过；新 ID 更长，已通过 Loadout 预算、JSON/HTTP/MCP、长 ID 小屏换行回归。数据库 PRIMARY KEY/UNIQUE 保留。此法消除已复现的确定性碰撞条件；随机源正确时碰撞概率极低，**不是数学上无条件唯一、跨重启时钟水位或分布式一致性保证**。
