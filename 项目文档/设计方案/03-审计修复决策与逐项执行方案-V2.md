## 2. F01：Frontmatter 只能作为 YAML 数据解析

### 报告依据

报告第 34–42 行：当前 matter(source) 会按文件语言选择 JavaScript parser；执行发生在 Zod 之前。仅 GET /api/inbox 已在隔离目录创建 marker，未调用真实确认动作。

### 本轮执行方案

当前继续保留 Markdown + Frontmatter 的最小实现，不做存储层重构。所有 Frontmatter 解析统一收口到共享安全入口，在进入解析器之前验证现行合法的 YAML Frontmatter 格式。拒绝非 YAML 及语言切换型 Header；不能仅把默认 language 设置为 yaml 后继续让文件覆盖。即使某个带语言标记的 Header 看起来仍是 YAML，也不得因此保留文件选择 engine 的能力。

明确调用 YAML-only 的数据解析路径，禁止任何代码执行能力，不保留通往可执行 engine 的隐式分派。读取当前锁定解析依赖的实际实现后，选择能证明满足该边界的最小路径；不能仅凭 API 名称声称安全。确需替换解析方式时说明必要性，不默认升级依赖。核对正常换行、中文和已有合法文档行为，不通过重写输入来规避校验。

现有 Zod Schema、Workspace、路径与 Hash 校验继续保留。Hash 仍对原文件实际字节计算，不因解析或换行处理而重写文件。逐一追踪 Scanner、Inbox、System Status、Confirm Preflight，以及其他实际发现的解析调用点，确认全部使用同一安全入口，不能只修复一个路由。

S01 可以作为同一解析调用的附带复核：明确关闭无需求的隐式全文 cache。具体 API 以 gray-matter 4.0.3 的实际代码为准，不能凭空传入一个看似有效的 cache:false。不要实现自己的新正文缓存。

### 验收

正式扫描、Inbox GET、System Status 和确认预校验都能安全拒绝对应非 YAML 样本；marker 不存在，正式区无新增或覆盖。合法 YAML、中文内容、已有 Frontmatter 字段和实际字节 Hash 结果保持一致。每个受影响入口都有回归覆盖，而非只测试孤立解析 helper。

### 不做

不为候选解析建立沙箱执行平台，不支持执行式 Frontmatter，不增加审批账本。本次不引入 PostgreSQL、pgvector、Revision/User/Permission/Relation/Audit 等未来对象；长期方向单独见第 13 节。

## 3. F02：定向读取与全量 Scanner 使用同一文件资格边界

### 报告依据

报告第 48–54 行：父目录变为指向仓库外的 Symlink 后，全量扫描拒绝，而基于旧 Catalog 的 Application Read 仍能读取；末级 lstat/O_NOFOLLOW 与相同 Hash 没有拦截该反例。

### 本轮执行方案

明确受信任 Repository 根，检查该根及根内到目标文件的每层目录，不只检查最后一级文件；再核对最终实际路径仍在允许边界内。沿用现行禁止 Symlink 的规则，即使链接目标在仓库内部也不能因 realpath 合法就放行。

将这项资格检查收敛到现有共享路径，供定向扫描及其 Search/Read/Mark Used/当前文件投影调用者复用。保留末级打开保护与现有文件一致性检查，不复制多套规则，也不能依赖 watcher 最终清理旧索引。

出现目录消失、替换或资格无法确认时，不返回正文、不执行 Used 写入。路径补丁目标是修复报告中的当前资格差异，不声称普通路径检查可以绝对抵御拥有完整本机权限的恶意并发替换。

### 验收

Repository 根、内部父目录、末级文件的 Symlink 场景分别覆盖；旧 Catalog 尚未刷新时也不能泄漏内容。普通编辑、合法移动和删除仍符合现行契约。拒绝路径不得被转换成另一个 Workspace 或宽松回退。

## 5. F04：按 Asset ID 计算差异，先删除受影响旧行，再写唯一新集合

### 报告依据

报告第 72–79 行：旧 A 被删除，旧 B 移入 A 的路径；正确 Snapshot 只有 B，但差异计算产生 changed=[B,B]，事务因路径唯一约束失败，重复同步仍 DEGRADED。

### 本轮执行方案

本项仍为独立索引算法问题。因用户第 4 项编号与描述不一致，默认先复核；用户明确指定“实施 F04”后才修改本项。不能用全局异常过滤、忽略 INSERT 错误或自动 rebuild 代替修复。

以已经通过 Scanner 的完整新 Snapshot 为目标，按唯一 Asset ID 计算两组集合：需要删除的旧行，和需要写入的新 Asset。删除、移动和同路径 ID 替换必须统一处理；同一个新 ID 只能写一次。

示例：

- 旧：a.md=ast301，b.md=ast302。
- 新：a.md=ast302。
- 删除受影响旧行：ast301、ast302。
- 写入新行：ast302，一次。

在同一事务里，先删除全部受影响的旧 Catalog/FTS 行，再写入唯一的新集合，并建立正确 rowid 对应。未变化行保留。两文件交换路径也必须成立。

不建议仅给 changed 做 Set 去重：必须同时证明旧行删除及路径交换语义正确。不要关闭唯一约束、绕过 READY gate，或把每次变更都改成整库重建。

### 验收

报告原反例、两个文件互换路径、路径被新 ID 复用、移动同时修改内容等组合场景，一次同步后 READY；Catalog/FTS 与有效 Snapshot 对应且没有旧条目。失败事务完整回滚。Task/Usage/binding 不变。

## 6. F05 + U04：可选知识故障不阻断 Prompt，资格失败不放宽权限

### 报告依据

报告第 85–91 行：缺失配置时真实 dist Hook 退出码为 2。报告已明确 N06 补充与非阻断降级目标冲突，未冒称实际观察 Desktop 被阻断。

### 本轮明确的处理边界

本知识 Hook 不是 Prompt 安全审查器。固定本轮方向：知识系统可以拒绝提供知识，但普通依赖故障不应替用户拒绝向 Codex 发送 Prompt。

用户所说的“全局异常过滤性处理”在本任务中限定为：**Hook 对外边界统一分类并映射错误，而业务层继续负责资格与不变量。** 不要求为整个应用新建全局异常框架；复用已有错误类型和映射点即可。MCP/REST 的非法知识操作仍按各自契约返回明确错误，不能为了 Hook 非阻断而全部改成成功结果。

| 情况 | 建议行为 |
|---|---|
| 正常处理 | exit 0，输出合法上下文 |
| 配置、数据库或投影等可选依赖不可用 | 非阻断降级；已处理的预期故障可 exit 0 + 极短诊断，不伪造 taskId 或注入旧知识 |
| taskId/Workspace 不合法 | 拒绝对应知识操作、不扩大权限；不把这等同于阻断整条 Prompt |
| 当前摘要超过预算 | 仅对仍有资格的条目降级本次输出，不超预算，不修改保存的 JSON |
| 非预期内部异常 | 保留明确错误记录，按目标客户端验证过的非阻断失败语义处理；不能全部吞掉并伪报正常 |

不要将所有 exit 2 机械替换为 exit 0 而不分类。同步更新冲突的 N06 完成补充和对应测试，使预期行为一致；原审计报告保留。

检查 SQLite busy_timeout 与重试次数，给可选 Hook 使用短等待上限并验证实际耗时。仅改变退出码却让用户长时间等待，也不符合轻量降级目标。不把异步超时包装当作同步数据库操作已被中断的证据。

U04 的执行规则：先完成 F03 资格过滤，再对剩余合格项进行本次投影，最后按最终实际渲染文本和现行统一字符计数口径验证预算。完整省略某个 DIRECT 摘要或把该项仅作为按需引用，不强行截断成易误导的半条规则。不访问不合格 Asset，不为装满预算另找其他 Workspace。不更改终态或已保存 Loadout，不把摘要展示算成一次完整 READ。极端情况下只输出极短可用性提示。

禁止的“兜底”：吞掉索引事务错误后伪报 READY；返回跨 Workspace 或陈旧内容；伪造 Task；把实际异常记录为业务成功；偷偷触发 F07 的离线重建或整库重置。

### 验收

缺配置、SQLite busy、目录不可读、摘要增长越界及错误 taskId，分别验证退出码、输出、无越权/伪造状态、无错误计数和实际等待。再用用户实际 CLI/Desktop 验证 Prompt 能继续；“Hook 子进程退出 0”不能替代真实客户端验收。

## 7. F06：watcher 真正 ready 后对账，再声明 READY

### 报告依据

报告第 97–102 行：初扫 Snapshot 与 watcher 注册之间写入新文件，ignoreInitial 不补报；状态 READY，但文件持续不可见，显式 synchronize 才恢复。

## 8. F07：显式离线 `rebuild-index` CLI

### 报告依据

报告第 108–114 行：底层 rebuild 已存在并验证保留 Task/Usage，但用户入口缺失；README 现有恢复方式为明确告知丢失历史的整库移动/重置。

### 用户已明确的边界

新增离线 **`rebuild-index`** CLI，作为人工或 Codex 诊断后选择执行的显式维护入口。它不是自动修复机制，不由 Hook、请求异常处理、watcher 故障或健康检查偷偷触发。

“显式”也不等于一发现错误就有权执行：Codex 诊断只读；针对真实运行库的维护执行，仍须在用户授权范围内。隔离回归可以按本项实施授权运行测试命令。

### 本轮执行方案

1. 使用现有 CLI 组织方式提供名为 `rebuild-index` 的薄入口，复用既有安全 rebuild 能力；确切 package/script/bin 调用以仓库实现为准，README 与构建产物烟测必须一致。本文件不声称该命令已经存在。
2. 明确离线前提：停止主服务，并确保同库 Hook/其他写入已停止。不能擅自 kill 进程、注销 Hook、修改用户 Codex 配置或把命令变成在线管理服务。无法安全满足离线前提时明确报告，不强行继续。
3. **只重建可派生索引。** Catalog、FTS 及其派生结构可以按既有逻辑重建；Task Loadout、Usage、Task Turn Binding 以及当前其他非派生运行数据全部保留，含 ID、字段值、JSON、状态、计数和关联，不能“删后重建空表”冒充保留。
4. 在写入前取得可信完整 Snapshot。处理删除/创建派生结构时保留事务与失败回滚，不动运行表的 Schema、约束或索引。
5. 入口应能到达可修复的 FTS/派生 Schema 故障路径，不能先被普通服务启动逻辑挡住，更不能为了启动维修而注册 HTTP 或 watcher、创建任务、写 Usage。
6. 完整运行库本身不可读、权限不足、离线条件不成立或无法完成重建时，返回明确失败。**失败不得自动升级为整库重置、移动整库、删除运行表或恢复成空库。** 本 CLI 不承载整库重置选项。
7. README 分开说明“仅派生索引恢复”和“完整运行库丢失/损坏”。后者的处理是另一种有数据损失风险的维护决策，不能作为本命令失败分支自动执行。

本条“不自动触发”针对离线 `rebuild-index` 维护动作，不禁止现行正常启动/增量 `synchronize`。F06 的 watcher-ready 后对账是正常索引一致性流程，不应被误删，也不能借此改成自动调用维护 CLI。

### 验收

- 运行构建后的实际 CLI，而非只调用内部方法；覆盖可修复的派生 Schema/FTS 故障。
- 前后 Task、Usage、Binding 及其他现有非派生运行数据逐字段一致，不能只比较行数；重建后正常 Search/Read 可用。
- 扫描整体失败或无法取得可信完整 Snapshot 时不进行破坏性写入；完整 Snapshot 中单个无效文件按既有资格规则排除，不为保留旧索引而返回无效内容。
- 重建中途失败时验证事务回滚与运行数据保留；完整运行库故障明确失败，不创建空库伪装成功。
- 所有异常降级与重试路径都未自动调用维护命令，未执行整库删除/迁移/重置。

## 11. W01：核查一个 Asset 是否支持多个 Workspace（只读，不扩展需求）

### 11.1 已知设计事实与未知实现

已读取的 Revision 2.1 第 8、9、10、11 节采用：

```text
AssetScope = GLOBAL | WORKSPACE

scope=GLOBAL
  → 不填写 workspace
  → assets/global/<type>/
  → 各 Task 的默认候选集合均可以包括它

scope=WORKSPACE
  → 填写一个 workspace 字符串
  → assets/workspaces/<workspace>/<type>/
  → Task.workspace 与之匹配时可访问
```

该设计的 `asset_catalog.workspace` 是单值字段，Frontmatter 示例也是单值；Search/Read/Mark Used 资格判断为 GLOBAL 或与可信 Task.workspace 相等。重复 Asset ID 的所有冲突文件应失去索引资格。

因此，**设计层面支持“单 Workspace 专属”以及“GLOBAL 全局共享”，没有表达“同一个 Asset 只属于 A、B，但不属于 C”的多对多契约。** GLOBAL 对多个 Workspace 可用，不等于任意多个 Workspace 的精确成员关系。

以上是已读取设计的事实，不是对用户最新代码的独立验证。原报告 F03 证明存在按可信 Workspace 进行投影资格校验的缺口，但不能仅凭该反例推断仓库完全没有新增多 Workspace 能力。

### 11.2 Codex 必须检查的内容

先定位当前设计、后续已确认决策及代码，而不只看一个字段：

| 检查面 | 必须回答 |
|---|---|
| Frontmatter / 公共 Schema | `workspace` 是字符串还是集合？是否存在 `workspaces` 或其他已定义成员关系？Zod 是否实际接受？ |
| Scanner / 目录 / Confirm | 一个文件如何确定所属范围？多 Workspace 如何落盘？同一 ID 多个文件实际如何诊断？ |
| Catalog / SQL / Repository | 仅单值字段，还是已存在 Asset—Workspace 关联结构？当前 SQL 是否真正使用该关系？ |
| Search / Read / Mark Used | 三者是否使用同一成员关系规则？未知 cwd 和 GLOBAL 的语义是什么？ |
| Task / Binding | 可信 Workspace 如何生成和复用？Task 跨 Session/Turn 不等于 Asset 跨 Workspace |
| Loadout / Hook / 投影 | 后续输出是否重新检查当前成员关系？是否仍存在仅按 ID 返回 metadata 的路径？ |
| Hub / REST / DTO | 是否只是全库筛选或人工管理浏览，而非 Asset 本身多归属？ |
| 测试与明确决策 | 是否存在 A/B 允许、C 拒绝的同一 Asset 测试？是否有用户批准的契约而非仅实现自行扩展？ |

特别防止四种误判：

1. `workspaces.json` 中有多个 Workspace，只说明配置了多个工作区。
2. 一个 Workspace 的 `paths` 有多个目录，只说明同一工作区可匹配多个物理位置。
3. 一个 Task 可跨多个 Turn/Session，不说明一个 Asset 可属于多个 Workspace。
4. 复制正文并使用不同 Asset ID，是不同 Asset；复制相同 ID 到多个目录，在现行设计下是重复 ID 冲突，不是共享机制。

### 11.3 输出必须给出的结论

结论从以下四类中选择，并给当前源码路径+行号、契约与测试证据：

- **SINGLE_ONLY**：当前只有 GLOBAL 或单一 WORKSPACE，与已知基线一致。明确不支持任意多个 Workspace 共享同一 Asset；F03 按当前规则修复。
- **MULTI_CONFIRMED**：当前确实存在后续已确认的多 Workspace 模型，Schema、存储、读取与测试都支持。列出完整契约，说明 F03 如何复用该资格规则；不退回旧的单值模型。
- **PARTIAL_OR_CONFLICT**：只存在部分字段/实现，或与已确认契约冲突。指出断点；不自作主张补完、删除或迁移。
- **UNKNOWN**：缺少足够证据。列明未获取的文件、路径或决策，不能因全局共享或变量复数就猜测支持。

报告中必须分别回答：一个 Asset 是否可同时用于 A/B；是否可以同时对 C 不可用；是否仍为同一 ID 和同一权威内容；当前可信 Task.workspace 对此如何判定。

### 11.4 本核查不授权的修改

不新增 `workspace[]`、`workspaces[]`、Asset—Workspace 关联表、权限表、共享 Workspace 协议或数据迁移；不把私有 Asset 改成 GLOBAL，不复制资产来模拟共享，不让调用方选择任意 Workspace，不改用户真实文件。

如果当前不支持，交付结论及最小需求缺口即可。是否需要在当前 MVP 增加“选择性多 Workspace 共享”，以及其精确语义，由用户另行决定。长期 PostgreSQL 方向也不自动授权该功能在本轮提前实现。

## 12. 异常、资格、投影与索引的责任划分

这一节用于回答“是否就是全局异常过滤与 Asset 投影判断”。可以共享边界处理，但不能合并根因：

```text
业务入口
  → 校验 Task 与可信 Workspace
  → 校验当前文件与 Asset 资格（F02/F03）
  → 对合格 Asset 构造本次输出并处理预算（F03/U04）
  → Hook 边界把可选知识故障映射为非阻断结果（F05）

文件 Snapshot
  → 按唯一 Asset ID 计算删除集合和写入集合（F04）
  → 同一事务更新 Catalog / FTS
  → watcher 与启动对账维护现有一致性（F06）

人工或 Codex 诊断
  → 明确维护授权与离线条件
  → 显式 rebuild-index（F07）
```

该图表示职责，不要求为每一行新建类/框架。F04 算法修复、F03 资格判断和 F05 异常映射可以复用现有结构，但必须各自有针对原反例的验证。
