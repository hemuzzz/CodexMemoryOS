## 3. Native Memories 与知识库的并行职责

### 3.1 责任划分

| 信息／能力 | 负责方 | 边界 |
|---|---|---|
| 当前对话中的上下文、临时计划和未完成推理 | Codex 当前上下文 | 不额外写成知识 Asset |
| 从过往任务回忆背景、偏好、工作习惯和一般经验 | Codex Native Memories | 使用客户端正常提供的能力，是否生成／可读由 Codex 和用户设置决定 |
| 需要明确维护的工程判断、业务约束、方案理由和可重复方法 | CodexMemoryOS | 经用户授权整理，候选人工确认后入库，按当前范围和文件资格访问 |
| 必须始终适用的项目指导 | AGENTS.md 或项目版本化文档 | 知识库和 Native 的召回均不能代替规则入口 |
| 当前源码／配置／测试结果 | 对应项目原件和运行证据 | 判断现状时核对；已确认知识记录目标和原因，不把实现缺陷固化成要求 |

Native Memories 不仅是短期缓存，官方也描述了跨任务背景和持久条目。因此不能用“Native=短期、知识库=长期”作为产品契约。跨项目也不是 Native 的独占范围：经用户明确选择的通用工程原则仍可成为 GLOBAL Asset；普通跨项目回忆无需因此再保存一份知识。

“Astra 中记忆有明显优化”作为用户当前使用观察记录，不作为本项目验证过的性能结论，也不把正确性依赖于某个模型版本。官方资料支持辅助回忆和后台生成的边界，没有在本次来源中提供 Astra 优化幅度的可复现证据。

### 3.2 并行指两种资料各自参与任务

1. Native Memories 按客户端既有机制提供历史背景，本服务不扫描或索引 Native 存储，不接管其生成模型、开关或文件。
2. 需要历史工程判断或确有未决工程选择时，通过真实 Hook Task 调用现有 Search／Read。已经从 Native 得到线索，也不把线索冒充当前 Asset Read；若结论依赖正式知识，仍应按资格读取当前原件。
3. 用户明确要求装配时才 Resolve；后续 Hook 继续读取已保存选择并核验当前内容。不因两路并行而自动 Resolve。
4. 普通事实只存在于 Native 一侧也可以完成任务，不要求每次同时命中两路。任一路不可用时，继续不依赖它的工作，如实说明实际缺失的证据。
5. Native 回忆与当前知识冲突时，先区分适用项目、时间和需求目标，再核对当前事实；不能仅凭新旧、热度或“已确认”字样自动胜出。影响当前决定且无法核实时，指出差异，不自动改写任一侧。
6. Native 内容只有经重新核验、明确整理和人工确认，才可能进入知识库；不自动同步 Session Summary，不双向同步，不统计 Native Recall／Read／Used。

“并行”不承诺每轮同时发起两次工具调用、统一排序或合并数据库，也不需要 MemoryProxy、Native 读取 API 或新的模型调用。

### 3.3 内容取舍

| 示例 | 是否进入知识库 |
|---|---|
| 今天修改了三个文件、测试失败一次、下次继续某任务 | 不进入，属于任务上下文或一般回忆 |
| 曾因重复回调导致重复入账，已验证为何采用数据库唯一约束 | 可作为 MEMORY 候选，记录条件、取舍和证据 |
| 一份需要完整阅读的架构设计 | 可作为 DOCUMENT；已有项目原件时优先引用，避免维护两份相同权威正文 |
| 多次复用且边界明确的排障流程 | 可作为 SKILL；库内类型不等于安装到 Codex 的可执行技能 |

当前没有待删除的 Session Summary 模块。需要修改的是定位、模板和使用协议的清晰度；Task／Binding／Usage 保留。既有知识不自动批量分类、迁移或删除。

## 5. 数据库双版本与本地 confirm

**用户已确定的方向：不依赖 Git；数据库每条知识只保留当前版本和上一版本；人工确认仍在 Codex 对话中完成，由本地 confirm 执行；Hub 不承担审核。** 本节固定产品边界，表结构和命令参数为拟议设计，尚未实施。原 Git 方案和多版本历史方案退出本期范围。

### 5.1 对象与职责

| 对象 | 保存位置与职责 | 默认检索 |
|---|---|---|
| 当前版本 CURRENT | 数据库保存最近一次 confirm 成功登记的完整内容快照 | 现有 Search／Read 仍按当前 Markdown 和资格执行，不新增数据库正文读取捷径 |
| 上一版本 PREVIOUS | 数据库保存被 CURRENT 替代的完整内容快照 | 不进入 Search／Loadout，只供变更对照 |
| 待确认的新稿 | 使用文件候选，不存为数据库第三个版本 | 不进入正式索引，不进入 Hub 审核流程 |

两版属于同一个 Asset ID，不创建两个可被默认搜索的 Asset。待确认文件不是历史版本；它可以反复修改，只有确切内容经用户确认并由 confirm 登记后才推进两版记录。

Markdown 继续作为当前知识的文件原件和现有读取入口；数据库保存的是**已确认内容快照**，不是可丢弃的 Catalog 缓存。正常完成 confirm 后，CURRENT 的原字节 Hash 必须与正式 Markdown 一致。上一版无法从当前 Markdown 重建，因此备份必须包含版本数据，不能再把整份 SQLite 视为可重建索引。

### 5.2 两版轮换规则

| 操作 | CURRENT | PREVIOUS |
|---|---|---|
| 首次确认 A | A | 不存在 |
| 确认 A→B | B | A |
| 确认 B→C | C | B；A 不再保留 |
| 内容未变化 | 保持原值 | 保持原值，不制造空版本 |
| 相同已完成确认的重试 | 验证已完成结果后返回，不重复轮换 | 保持原值 |
| 审核前拒绝、Hash 不符、目标漂移 | 不变 | 不变 |

Hub 对照 PREVIOUS 与 CURRENT，回答最近一次已登记变更；首次新增返回“没有上一版”。不提供任意历史版本选择、不保留每次草稿、不新增回滚入口。两版之外的旧正文淘汰是该保留策略的明确结果，不额外维护隐蔽版本库或用 Git 补足历史。

### 5.3 拟议数据库模型

建议增加独立持久化表 `asset_content_version`，每条 Markdown 以 Asset ID 关联最多两条记录，用版本状态区分当前应用版与上一历史版，不引入新 ID 类型、版本链或审批账本：

| 字段 | 含义 |
|---|---|
| `asset_id` | 同一知识的现有 Asset ID |
| `version_status` | `CURRENT`（当前应用版）或 `PREVIOUS`（上一历史版，仅一条） |
| `raw_content` | 完整 Markdown 原字节，建议 BLOB 保存，不规范化换行或 Unicode |
| `content_hash` | 原字节 SHA-256，必须与 raw_content 一致 |
| `recorded_at` | 本次版本登记时间，不当作经过身份认证的人审证明 |

主键 `(asset_id, version_status)` 加 `version_status IN ('CURRENT', 'PREVIOUS')` CHECK 约束，从数据库限制同一 Asset 最多两条、每种状态最多一条。版本状态只属于数据库，不加进 Markdown Frontmatter；历史版特指上一版，不代表所有历史。CURRENT 推到 PREVIOUS 时保留其原内容、Hash 和登记时间；新 CURRENT 使用新的登记时间。只有存在真实上一版才写 PREVIOUS，不写空正文占位。

数据库事务内完成淘汰旧 PREVIOUS、移动 CURRENT、写入新 CURRENT；任一步 SQL 失败回滚整个事务。业务层负责不变内容去重和基线校验，不能靠固定两个槽位解决所有并发问题。

Catalog／FTS 重建必须保留此表，不能通过 Catalog 外键级联删除版本；版本表缺失或损坏不能用索引重建悄悄恢复为“历史完整”。已有 Task／Usage／Loadout 模型不扩展为版本账本，本期 Used 仍是 Asset 级声明，不能由此宣传历史使用正文可重放。

### 5.4 确认位置不变，扩展现有本地入口

人工操作保持：在 Codex 对话中查看完整新稿和必要 Diff，明确确认确切内容；Codex 再调用本地 `asset:confirm`。没有 Hub 批准按钮、审核列表、审批状态或确认 MCP 工具。

现有 confirm 仅支持新 Asset 的 no-clobber 移动，不会因为保留同一个命令名就自动具有更新能力。拟在同一 CLI 中区分新增和更新：

- 新增：沿用现有候选路径和 `expected-content-hash`，继续拒绝目标覆盖；成功时只登记 CURRENT。
- 更新：必须显式指定更新意图、目标 Asset ID、当前正式基线 Hash 和新候选 Hash；不能仅因 ID 已存在就自动进入覆盖分支。目标路径从当前合法 Asset 解析，不接受任意输出路径。
- 更新候选可保留目标 Asset ID，但只由更新分支识别与校验。普通 Inbox 列表仍不把同 ID 冲突项变成可新增候选；本期不因此扩展 Hub 审核或静默放宽原有新增资格。
- 更新分支第一期只处理同 ID、同类型、同 Scope／Workspace 的内容修改；跨范围、改名和类型迁移不借此获得授权。
- 新稿和正式基线都按实际原字节复核。审核后任一方变化，重新展示 Diff 并绑定新的内容身份，不沿用旧确认。
- 为双版持久化，confirm 后续需要数据库配置。这是相对当前“只需要仓库和 Workspace 配置”的实际命令依赖变化，实施时须同步 README 和命令测试，不能写库失败却返回完整成功。

本轮不冻结参数拼写，也不修改当前可用 CLI；这里固定的是输入语义与已有新建行为的兼容要求。

### 5.5 Markdown 与数据库的一致性及失败边界

只用 SQLite 事务不能使文件替换也原子提交。实现至少满足：

1. 写入前保留已读取的正式基线和新稿原字节，重新校验当前文件、路径资格和数据库 CURRENT；并发确认必须对同一基线作条件更新，不能让两个更新都把自己当作紧邻下一版。
2. 新内容、旧内容和数据库轮换对应同一次授权更新；正常成功返回时正式文件 Hash 与 CURRENT 一致。
3. 参数／资格／Hash 拒绝不得改写任何一版或正式文件。执行中失败必须区分“尚未生效”和“发生部分写入”，不能统称成功或盲目再次轮换。
4. 部分写入保留可恢复的新稿与可用基线，只能按实际内容身份恢复或补完；不得覆盖用户在失败之后另行修改的内容。
5. 相同调用重试先核对文件与双版的实际状态，已完成不再次轮换；状态无法确定时返回明确错误，停止该次更新。
6. 文件替换、数据库提交的具体顺序、进程崩溃恢复及写入者协调仍需在实现前完成针对性技术设计与隔离反例验证。本节不声称已经解决跨存储原子性，也不为它提前新增通用事务或审批平台。

**外部编辑的兼容边界单独保留：** 当前人直接编辑正式 Markdown 会立即生效，这一点尚未被用户本次决定明确取消。本设计不擅自改成“只有 confirm 才可读取”。数据库 CURRENT 因而准确表示“最近一次 confirm 登记的版本”；外部保存不自动登记版本，也不冒充人工确认。

若当前文件 Hash 与数据库 CURRENT 不同，Diff 返回明确的内容不一致状态，不将数据库旧快照宣传成当前文件，也不由 Watcher 自动接受变化。如何把外部修改纳入 confirm，或是否改为所有正式修改都必须经过 confirm，需要单独确定；在此之前不承诺捕获任意文件覆盖的每一版。这个边界不影响本轮已经确定的确认位置和数据库最多两版。

### 5.6 Hub 只读 Diff 的数据契约

拟提供 `GET /api/assets/:assetId/diff`，不再接受 Git ref、任意历史版本或文件路径。先核对当前 Asset 的资格以及当前 Markdown 与 CURRENT 的 Hash 一致性，再在一个一致的数据库读取快照内取得两版。

| 结果 | 含义 |
|---|---|
| `AVAILABLE` | 两版齐全且对应当前正式内容；返回两版 Hash 及完整文本差异 |
| `NO_PREVIOUS_VERSION` | 只有已登记 CURRENT，没有上一版 |
| `UNTRACKED` | 既有合法 Asset 尚未建立版本基线，不把未登记误报成“没有变化” |
| `CONTENT_MISMATCH` | 当前 Markdown 与已登记 CURRENT 不一致，不返回误导性的成功 Diff |

当前文件不可访问时沿用现有详情拒绝，不能借历史正文绕过范围；数据库不可用或损坏按运行错误处理，不伪装成首次新增。响应只包含比较需要的两版内容身份和行级差异，不添加审批／投放状态。对照比较 Frontmatter、正文及换行；Hash 与 Diff 必须来自同一份字节，不能再次读取文件拼接结果。

历史正文只供 Hub 个人本地浏览；不新增模型历史读取工具，不改变现有 Task Workspace 资格。只读 Diff 不推进版本、不写 Used，也不承担修复或审核功能。前端布局、组件和适配继续留待整体重做。

### 5.7 原字节与差异结构（采纳审查 R01 的非 Git 部分）

数据库 `raw_content` 保存 confirm 同次合格读取的原始字节，Hash 也从该字节计算；禁止把现有 `markdown` 字符串重新编码后冒充原始字节。当前 Scanner 在内部持有 Buffer，但 `readLibrary` 对外返回 string＋Hash；未来需在纯内部读取结果中保留原字节，旧详情 HTTP DTO 不必因此改变。

源码依据：`asset/scanner.ts` 使用 `new TextDecoder("utf-8", { fatal: true })` 解码，再返回 `markdown: source`。相同解码配置的最小实验表明 UTF-8 BOM 会被移除。因此版本持久化必须在解码前取得字节；不能通过按路径再读一次来补齐，避免 Hash 与正文来自不同文件状态。此实验只验证解码行为，不代表新版 confirm 已实现或验收。

MVP Diff 只处理合法 UTF-8，不自动猜测或转换编码。比较阶段采用保留 BOM 的解码方式（例如 `ignoreBOM: true`），不作 trim、换行归一化或 Unicode normalization。BOM 保留为首行 text 的 U+FEFF，并在响应中附两侧 `hasUtf8Bom` 标记；这是原文差异，不是噪声自动清理。

`AVAILABLE` 响应固定包含 `assetId`、本次当前文件的 `relativePath`、`previous`／`current` 元数据（各有 contentHash、recordedAt、hasUtf8Bom）、`hasChanges` 和完整 `hunks`。`hasChanges=false` 当且仅当两侧原字节相同，此时 hunks 为空；原字节不同且 AVAILABLE 时 hunks 必须非空，包含换行或 BOM 等差异。当前文件不存在或当前资格拒绝时不得用历史响应绕过。

每个 hunk 的结构：

| 字段 | 规则 |
|---|---|
| `oldStart`、`newStart` | 各自原文中的一基行号；计数为 0 表示在该行之前插入，可为该侧总行数＋1 |
| `oldCount`、`newCount` | 该块分别消费的原文行数，非负整数；context 同时消费两侧 |
| `lines` | 有序差异行，每行含 `kind: context/add/delete`、不含结束符的 `text` 和 `eol: LF/CRLF/CR/NONE` |

以 text＋eol 作为完整行比较单元；CRLF→LF 必须产生 delete/add，不能因为文字相同就显示无变化。context 要求两侧完整行相同。空文件为零行；末尾有结束符时不虚构额外空行；NONE 只用于最后一个没有结束符的行。JSON 转义不改变字符串的原始语义，不返回 HTML。

除 §5.6 的四种状态，增加稳定的非成功比较状态 `UNSUPPORTED_ENCODING`、`INPUT_LIMIT_EXCEEDED`、`WORK_LIMIT_EXCEEDED`、`OUTPUT_LIMIT_EXCEEDED`。所有非 AVAILABLE 结果不带 hunks，不给 `hasChanges=false`，避免“没完成比较”被理解为“无变化”。最小响应只返回 assetId 和 status，不拼凑部分成功元数据。非法请求、当前资格拒绝和意外错误继续使用现有 REST 错误外壳。

读取的版本正文与其已存 Hash 不符时，按版本数据完整性错误处理，不当成无上一版或编码不支持；数据库读取异常同样不能降级为空 Diff。合法但不受支持的编码才返回 UNSUPPORTED_ENCODING。

### 5.8 比较资源边界（采纳审查 R02 的非 Git 部分）

Git 子进程及其超时已退出设计，不能把旧的 3 秒条款搬成新 Diff 的计算保证。数据库只有两条记录，也不意味着正文、行数或响应天然有界。

拟议最小限制如下；它们只限制可选 Diff，不改变普通 Asset Read、正式文件资格或版本正文保存上限：

| 阶段 | 初始设计上限与行为 |
|---|---|
| 版本原文读取 | 单侧 1 MiB；在同一数据库读事务内先检查 BLOB 长度，再读取正文，超限直接 INPUT_LIMIT_EXCEEDED |
| 解码和拆行 | 单侧最多 2,000 行，超过即 INPUT_LIMIT_EXCEEDED；包含混合换行和空行 |
| 比较计算 | 实现必须有显式、可验证的工作量上限／中止入口；不能用 Promise.race 或同线程定时器冒充同步计算抢占 |
| 差异构造与响应 | 最多 4,000 条输出差异／上下文行；完整 JSON 外壳最多 8 MiB，预算包含转义后的文本和元数据；超限返回 OUTPUT_LIMIT_EXCEEDED，无部分成功 |

计算库或算法尚未选定：B 开始编码前需选择支持工作量中止的实现并明确上限单位和值，或用更小输入范围证明同步计算有可接受上界。上限以隔离最坏样本验证，不能凭文件字节数宣称服务不会阻塞。若候选实现无法满足，再评估可终止的执行单元；不默认增加线程池、任务队列或新的执行平台。

响应构造要在累计 JSON 编码成本时及时停止，不先制造无界结果再检查；最终仍检查实际序列化字节数。数据库长度检查和正文读取须使用同一快照，不能长度检查后换一版更大的正文。工作量中止返回 WORK_LIMIT_EXCEEDED，意外异常不伪装成预算耗尽。

验证需要包括超多短行、重复行、几乎完全不匹配的两侧、JSON 高转义开销、连续及并发请求后的资源释放，以及同期普通 REST／MCP 请求的响应。测试前提和观察到的耗时要记录，不将某台机器结果写成通用绝对时限。

### 5.9 既有知识与数据库维护

已有 Asset 不自动伪造历史。未来可在单独授权的初始化中，将当时合法的正式文件登记为 CURRENT，PREVIOUS 缺失；该登记是既有文件基线采集，不声称重新取得了历史人审记录。初始化未完成时保持现有读取可用，Diff 返回 UNTRACKED；实际初始化方式和范围不在本轮执行。

数据库丢失时，当前文件可以重新采集当前基线，但无法恢复上一版；备份／恢复需要同时考虑 Markdown 和版本表的一致性。本期不自动删除 Asset、清理孤立版本或迁移真实数据。未来实施时需更新“SQLite 只保存派生索引和非关键运行数据”的旧说明，明确版本快照是需保留的持久数据。

## 6. 过时、修正与替代的最小维护

以更新当前知识为默认路径：同一主题纠错、条件改变或方法改进，保留 Asset ID，更新当前结论、适用条件和 summary，在“本次变更说明”保留简短理由。数据库只保留当前版与上一版，更早正文不保留；不在正文无限追加每次版本。

整条旧结论不再适用时，正文与 summary 必须先明确“原结论不再适用”，再给替代判断或已确认的来源引用；不能只在文末注明过时，而让摘要继续投影旧建议。存在独立新主题时，可经现有流程新增另一 Asset，再由用户授权修正旧条目的指引。

替代引用是普通正文引用，不增加关系实体；它也不扩大 Workspace 范围。不要自动读取当前 Task 不可访问的目标、在 GLOBAL 中泄露受限知识的内容，或因目标不可访问而改用 Hub 绕过模型边界。跨范围关联不是本期自动维护能力。

没有状态字段和自动过滤器，因此“需复核／已不适用”的条目仍可能被搜索命中。本期通过整理与人工复核，要求摘要和正文明确撤回不适用的建议；系统不自动认证内容正确性，不保证人工维护已正确完成，也不自动过滤全部过时条目。需要停止索引、移动或删除旧知识时仍需独立明确授权，本期不增加自动处置。

不按文件修改时间或长期未使用推断失效，不按 Recall／Read／Used 计数自动替代、晋升或删除。用户判断具体条件已经变化后，才整理更新。

### 跨存储协议

- 所有确认使用同一已配置 SQLite，`BEGIN IMMEDIATE` 协调写入者，锁忙立即返回 `CONFIRM_BUSY`，不在同一事件循环同步等待另一个确认。正式 Asset、Inbox 和 CURRENT 在锁内重新校验；更新必须同时匹配正式 Hash 与 CURRENT Hash，不接受未登记或已外部修改的基线。更新候选与目标的相对路径除根目录外必须一致，防止借更新改名。
- 在改正式文件前，以 `O_EXCL/O_NOFOLLOW` 写入并 fsync 仓库根 `.asset-confirm-recovery.json`，保存本次输入身份、新稿及基线原字节。它是单次未完成操作的恢复材料，成功即删除，不是历史/审批账本。新增继续使用原 no-clobber 流程；更新把同一合格 Buffer 写入临时文件、fsync，再复核双方资格和 Hash，rename 到原正式路径。
- 正式文件及目录 fsync 后，在 SQLite 同一事务内轮换两槽位并提交。正常成功复核正式文件，按 Hash 清理候选及恢复文件。CURRENT→PREVIOUS 保留原登记时间；相同字节不轮换。数据库 `user_version=1` 标识该持久表已安装，随后表缺失或结构/内容 Hash 损坏按错误处理，重建 Catalog 不修复历史。
- 崩溃时 SQLite 回滚未提交事务，恢复文件留下两侧字节。同一输入重试：正式文件仍为旧版时重新验证并执行；正式文件已为新版而 CURRENT 仍旧时，仅补完数据库轮换；文件与 CURRENT 均新版时，只核对相邻基线并完成清理，不重复轮换。新增完成后的同 Hash 重试也可识别。候选、正式文件、数据库或恢复身份不符时停止，保留可用恢复材料，不覆盖后来编辑。
- Hash/资格拒绝且能证明没有生效时保持正式文件和版本不变；不确定或部分落盘返回 `CONFIRM_PARTIAL_WRITE`，恢复材料本身异常/调用不符返回 `CONFIRM_RECOVERY_REQUIRED`。恢复文件写入中断或临时文件身份不明时需人工检查，不猜测其内容。没有自动回滚、回退到旧知识或通用事务平台。
- 支持边界是本机本地文件系统、同一仓库使用同一数据库。SQLite 锁协调本系统确认进程；任意外部编辑器不会遵守该锁，文件路径检查与 rename 之间仍不是 OS 级比较交换，不能承诺抵御同一瞬间的恶意父目录替换/非协作写入。外部静态修改继续由当前资格读取生效，Diff 报不一致；恢复绝不以旧快照自动覆盖未知 Hash。进程中断测试不等于断电、磁盘损坏或网络文件系统证明。

### 有界 Diff 选择

先检查数据库 BLOB 长度并在同一读事务内取两版、核对 Hash。合法 UTF-8 保留 BOM；完整 text+eol 行单元先驻留为整数 ID，再作 LCS。一个工作单位是一个 DP 单元计算或回溯一步，预算 1,000,000；分配 DP 前检查总上界，循环仍显式计数中止。输入字节/行数、输出行数/JSON 大小沿用 §5.8；单个完整上下文 hunk 能重建两侧原文，不作局部截断。长重复文本不在二次循环内重复比较字符串；上限内最坏 DP 数组约 2 MiB。JSON 预算包含 REST 外壳、转义和元数据，并在逐行构造时检查，末尾再检查实际序列化大小。

验证证据见 [双版确认与 Diff 验证](../验证记录/03-双版确认与Diff验证.md)。
