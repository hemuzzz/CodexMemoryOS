# 知识评估标准与 Stop 兜底设计

日期：2026-09-10。状态：**已按本设计完成开发、本机配置和服务重启；隔离验证通过，CLI 三个 Hook 已信任并 Active。Desktop 新回合自动行为待验收。** 实施证据见[验证记录](../验证记录/08-知识评估Hook实现与安装验证.md)。

本文是[2.4 核心设计](05-知识召回核心模型与Task解耦设计.md)的交付流程补充，承接[知识内容模型](../../工程约定/知识内容模型.md)，不改变 Recall、Read、Used 和人工确认契约。

## 1. 需求理解与范围

本次是两项现有功能优化：

1. **先修正“无增量”的判断标准。** 项目文档已有记录，不代表可复用判断已经完整覆盖、以后可以正常找到；但也不要求把所有文档复制成 Asset。
2. **再加 Stop Hook 防漏提醒。** 主 Agent 在工程交付前完成评估；Hook 发现已观察到工程活动的回合缺少记录时提醒，允许结束。

首版采用“轻量知识评估＋本地结果记录＋非阻断提醒”。主流程仍要求工程交付前评估，但程序不保证每次评估都完成：缺失只提示，不自动补跑、不创建新的模型轮次。成功标准为：无增量有具体依据；失败不冒充无增量；观察范围内的遗漏可见；普通交流不为评估打卡，候选待确认和知识故障不阻断交付。

配套限于一份小型本地评估记录和两个一次性标记：本轮观察到活动、已经提醒。首版不恢复 Task/Loadout，不新增数据库表、MCP 工具、Hub 页面、模型服务、评审 Agent、全量对话扫描或知识质量评分系统。

### 1.1 本次评审的采用与订正

依据[“知识库项目”最新设计评审回复](https://chatgpt.com/c/6a9b85dc-6ff4-83ec-8ba8-9f0b440da947)，作以下收敛。评审内容是设计建议；本文结合当前源码与宿主协议确定可执行的含义。

| 评审意见 | 本文决定 |
|---|---|
| 首版用提醒替代强阻断 | 采用；移除自动补跑、`recoveryRequested` 与跨续跑链路绑定。评审后文的“最多补一次”与此前“不阻断”不一致，首版明确不补跑 |
| 普通交流不进入评估链 | 采用；无需提交 SKIPPED 或调用记录 CLI。用实际工具活动缩小提醒范围，不把所有 Stop 都视作工程交付 |
| UserPromptSubmit 判断本轮是否修改、测试 | 订正时序：该事件发生在工作开始前，无法观察未来动作；改为 PostToolUse 只记一个活动标记 |
| 仅工程变化需要评估 | 保留只读审查、诊断、解释和设计形成的可复用判断；是否改文件不是知识价值的充分或必要条件 |
| 简化四状态 | 保留四种短结果，将 INCOMPLETE 表达为 FAILED 并附原因；不建立状态流转。四个名称换成另外四个名称，本身不减少复杂度 |
| 不自动生成候选 | 理解为不每轮强产候选、Hook 不生成候选；主 Agent 经评估发现有价值且获授权的增量时，仍沿用既有自动准备 Inbox、人工确认正式入库的规则 |

以下消融是反事实设计分析，未进行代码 A/B 或真实成本实验。删掉阻断与补跑后，提醒仍可工作；删掉全部本地记录后无法机器区分本轮与旧轮；删掉活动标记后只能在“所有回合都提醒”和“同时漏掉活动与评估时保持沉默”之间选择。首版保留活动标记用于筛选提醒，不扩展为任务识别系统。

## 3. 先改评估标准

### 3.1 评估对象与顺序

主 Agent 利用当前工作上下文，检查是否新形成或修正了以下内容：可复用结论、适用条件、架构取舍、反例、排障方法、验证边界。完成交付、阶段性交付和受阻交付都覆盖，但只评估已核实的结果。

先提炼可能的知识点，再决定是否需要对照知识库：

- 没有潜在知识点：说明具体原因，直接结束轻量评估，不作空检索。
- 有潜在知识点：复用本轮仍适用的 Recall/Read；不足时仅补充相关查询和正文比较。无命中不等于全库无历史。
- 有新增复用价值：沿用现有新增或修订候选流程；候选与正式确认分开。
- 关键证据、访问能力或去重依据不足：明确未完成部分，不能改写成“无增量”。

判断单位是内容，不是操作名称。“重构”“失败实验”“只改文档”都可能产生知识；已确定方案的机械实施也仍做短评估，只是不展开完整提炼。

### 3.2 “无增量”必须说明什么

| 可成立的原因 | 必须说明的依据 |
|---|---|
| 已有知识完整覆盖 | 指出已核对的 Asset，并说明本次未改变结论、条件、反例或验证边界；不要求重复 Read |
| 仅执行已确定要求 | 点明执行的要求，以及没有形成新取舍、新异常或新方法；不能只写“机械修改” |
| 仅为一次性状态 | 说明为何只是临时计数、进度或环境现象；若形成可重复诊断方法，仍有潜在增量 |
| 项目原文已是合适的权威来源 | 指出具体文档及章节，说明它已完整表达可复用判断、未来如何正常找到，以及另存一份为何没有增量价值 |

最后一项必须同时核对**内容覆盖**和**后续发现路径**。例如长期规则已经由 AGENTS 明确引用，并会在相应任务中加载，可以保留原件；一次验证记录只有“删除模块，测试通过”，并未说明为何可删、适用前提和重新引入条件，不能据此排除知识增量。

只有当前对话中的文件链接、一个目录索引，或“以后可以全文搜索”，不能直接证明发现路径已经足够。若有独立判断值得以后通过知识库召回，优先提炼简短 MEMORY 并引用项目原文；需要文档导读时可按现有 DOCUMENT 类型整理。两者都走现有候选流程，不新增目录索引器，也不复制整份权威文档。

以下表述不能单独构成无增量理由：“文档已经写了”“搜不到”“测试都通过了”“只是一次重构”。Hook 不通过关键词黑名单审核这些自然语言理由，判断质量仍由主 Agent 和后续抽查负责。

### 3.3 本轮评估的四种结果

以下是本地记录的四种结果，不是 Asset 生命周期或数据库枚举，也不建立结果间的迁移规则。

| 结果 | 含义与必要内容 | Stop 行为 |
|---|---|---|
| `SKIPPED` | 已观察到工具活动，但主 Agent 判断本轮仅为澄清、进度等非交付内容；写明原因。无活动的普通交流无需此记录 | 放行 |
| `NO_INCREMENT` | 已评估，符合上表具体理由 | 放行 |
| `CANDIDATE` | 有新增或修订建议；引用已准备的 Inbox 候选。明确只读时可引用当前交付中的具体建议，注明未写入 | 放行，不等待正式确认 |
| `FAILED` | 评估或必要核对未完成；包括证据不足、读取失败、候选准备失败。说明具体缺口，不暗示已经判定无增量 | 提醒后放行 |

“新增／扩展修订”仍由现有 capture 流程决定。`CANDIDATE` 在主 Agent 完成候选准备或交付具体只读建议后记录；有意向但尚未完成必要步骤时使用 FAILED。没有记录与执行失败都允许结束，但事实不同：Hook 不把缺记录补造为 Agent 已评估失败，也不代写 SKIPPED 或 NO_INCREMENT。

## 4. Hook 所需的最小本地记录

### 4.1 为什么需要记录

当前没有可以直接复用的评估事实。最终回复中的“已评估”、Recall/Read/Used 调用和 Inbox 文件存在，都无法区分本轮完成、上一轮完成或仅做过部分步骤。

新增薄的本地 CLI `capture:assess`，接收结构化 JSON，通过现有命令工具调用。它只校验并保存结果，不检索、不创建候选、不调用模型，也不授予 Workspace 能力。工程交付写一份结果；普通无活动交流不调用。宿主提供的直接包装命令优先，避免额外包管理器启动成本。

| 字段 | 来源与用途 |
|---|---|
| `sessionId`、`turnId` | 主 Agent 使用 UserPromptSubmit 提供的本轮标识；Stop 使用自己的宿主输入比对。只用于本轮归属，不维护跨轮任务绑定 |
| `outcome` | 上述四种结果之一 |
| `reason` | 与本轮结果对应的短理由或具体缺口 |
| `references` | 按需引用 Asset ID、本轮 Read/Recall 引用、项目文档章节、候选路径和 Hash，或只读建议的位置 |

保存到包装脚本固定的运行缓存目录，按 Session/Turn 摘要隔离，不新增知识 ID。每轮只使用 `assessment.json` 及可选的 `activity.flag`、`warned.flag`：分别由记录 CLI、活动 Hook、Stop 写入，避免多个入口覆盖同一 JSON。两个标记不含正文，以排他创建保持幂等；结果文件用临时文件原子替换，重复提交覆盖本轮结果。

记录只保留简短理由和引用，上限 8 KiB；reason 最多 2000 字符，references 为至多 16 个非空字符串、各至多 1024 字符。Session/Turn 为 1–128 位标识（字母数字开头，其后允许字母数字、点、下划线、冒号和短横线）。不保存对话、命令、工具输出或能力原值，不进入 Git、Catalog、FTS、Usage 或 Hub；首版不建历史报表、清理服务或初始化握手。重复 UserPromptSubmit 不重置本轮文件，后续正常新轮使用不同键。

CLI 只校验身份字段格式、合法结果、非空理由和引用结构；CANDIDATE 必须有候选或只读建议引用。无增量四种理由留在 Skill 中，不再增加 `noIncrementBasis` 枚举，也不通过自然语言猜测其分类。记录能证明声明已提交，不能证明评估实际充分、引用存在或内容正确；正文比较与候选 Hash 核对仍走既有 capture/Read 流程。

### 4.2 记录的保证范围

旧轮记录不能满足新轮检查。理由是否充分、SKIPPED 是否误用、候选是否有价值仍是语义判断；把同一句“已评估”写进 JSON，并不会让它自动成为真实评估的证据。

**同轮过期首版采用流程约束：** 主 Agent 在最后一次会影响结论的修改或验证之后提交记录；之后若继续修改实现、收到新需求或形成新证据，必须重新评估并覆盖记录。评估和 Used 结算等收尾动作本身不递归触发新一轮评估。

活动标记只用于筛选提醒范围，不能证明评估仍然有效。首版不跟踪工具序列、不自动使评估失效、不计算 Git 工作树 Hash 或扫描对话；同轮后续变化仍由主 Agent 更新记录。若真实使用暴露此类问题，再评估增加失效机制。

## 5. 活动筛选与非阻断提醒

### 5.1 谁需要评估，谁需要提醒

**评估义务按交付内容决定，Hook 提醒范围按可观察信号筛选。两者不等价。** 主 Agent 仍评估完成、阶段性或受阻的工程交付，包括只读审查和设计；纯交流不要求评估或写记录。

UserPromptSubmit 仅保留能力交付并补充本轮标识和短指引，不判断未来行为，不写默认 SKIPPED，也不初始化每轮文件。

PostToolUse 首版匹配 `Bash` 和 `apply_patch`，工具返回后只创建 `activity.flag`，失败工具也计入可观察活动。`exec_command` 的 Bash 映射、Edit/Write 别名及 code mode 内嵌调用按真实宿主覆盖验证。后续匹配命中不累加次数、不保存输入输出、不向模型注入信息。[官方工具覆盖与 PostToolUse](https://learn.chatgpt.com/docs/hooks#tool-coverage)

工具活动只是提醒线索：一次 `pwd` 也可能被计入，浏览网页或纯对话中形成的架构判断则可能没有标记。主 Agent 可在没有活动标记时主动提交工程评估；若既无标记又漏交记录，首版不会发现。这是减少普通交流开销所接受的覆盖限制，不能称为所有工程交付自动识别。首版不解析 shell 命令、不为覆盖所有工具新增分类器。

### 5.2 正常收尾与异常

主 Agent 完成工作后按第 3 节评估，有价值且获授权时沿用候选准备流程，提交结果再交付。Stop 对照真实宿主 Session/Turn 读取缓存：

| 本轮情况 | Stop 行为 |
|---|---|
| 无活动标记、也无评估记录 | 安静结束；只是未进入机器观察范围，不声明已评估或确定无增量 |
| 有合法 SKIPPED、NO_INCREMENT 或 CANDIDATE | 安静结束，候选待确认不提醒 |
| 有活动标记，但缺记录 | 提示“本轮观察到工程相关工具活动，但未找到知识评估记录”并允许结束 |
| 记录身份不符、损坏或结构无效 | 提示记录无效并允许结束，不把旧轮结果当成本轮结果 |
| 有 FAILED | 提示评估未完成及简短原因并允许结束 |
| 缓存读写失败、宿主标识缺失或检查超时 | 如实报告检查不可用并允许结束，不伪造评估结果 |

正常返回 `{}`，需要提醒时返回 `{"systemMessage":"简短提醒"}`。正常存储条件下，通过排他创建 `warned.flag` 保证同轮最多提醒一次；标记创建失败时报告检查异常，不能再保证提醒去重，但仍不阻断。

两个新增 Hook 均不返回 `decision:block`、退出码 2 或 `continue:false`，不改变工具结果、不发起补跑、不调用模型、不检索或生成候选。它们不装配 KnowledgeRepository，不依赖 MCP 服务存活。用户中断、客户端退出和进程崩溃不受结束提醒保障。

### 5.3 成本边界

普通无活动交流没有额外评估或记录工具调用，Stop 仅检查本轮缓存。工程交付复用现有上下文做短评估并记录；有知识点才展开 Recall/Read 和候选整理。提醒本身不主动启动新模型轮次，但若进入后续上下文仍可能占用 Token。

新增成本还包含每次匹配工具后的本地 Hook 启动，不能只统计 Stop。首版测量“匹配次数×活动 Hook 耗时＋记录 CLI＋Stop”，与实际模型额外轮次分别报告。单次 Hook 尽量在 200 ms 内完成、约 1 s 超时降级是初始目标，需计入进程启动验证；没有实测前不承诺总耗时或固定 Token。活动标记同步落盘，避免异步 Hook 晚于 Stop 导致漏检查。

实现未引入初稿的补跑标记、重试链路、每轮初始化或无增量原因枚举。两个新增事件走独立 `capture-cli`，已有 `handleCodexHook` 仍只负责 UserPromptSubmit。版本化包装脚本位于 `integrations/codex/`，本机提交脚本转发到对应版本化入口。Hook 定义变化仍须走宿主正常信任流程；本次已通过 CLI `/hooks` 完成。[官方 Hook 信任说明](https://learn.chatgpt.com/docs/hooks#review-and-trust-hooks)

## 7. 验证与放行标准

### 7.1 评估标准回放

| 样本 | 预期 |
|---|---|
| “删除模块、验证通过”，文档没写取舍与重新引入条件 | 不得以已有文档判无增量；检查实际证据，形成候选或明确不足 |
| 已有 Asset 完整覆盖，本次仅执行原约束 | 复用已有 Read，说明覆盖范围，判无增量 |
| 原文是规则入口明确引用的权威说明，内容与复用路径均充分 | 可说明依据后判无增量，不复制全文 |
| 机械修改但遇到并查明一种新故障 | 按新故障判断，不因“机械”跳过 |
| 相关知识读取失败，或仅有未验证的实施猜测 | 标为未完成，不伪装无增量 |
| 只读审查形成有价值结论 | 展示具体建议及证据，不要求写 Inbox 才能结束 |

以上检验判断质量，需要用带有工作证据的真实或明确标为模拟的样本回放；程序测试只能证明记录校验和分支行为，不能证明模型每次判断正确。

### 7.2 隔离程序检查

只覆盖三组必要行为：

- 结果记录：四种结果、非空理由、候选引用要求、身份不符和损坏；无记录不能凭最终回复的“已评估”通过。
- 活动与提醒：普通无活动交流静默、有活动缺记录提醒、有 FAILED 提醒、SKIPPED/NO_INCREMENT/CANDIDATE 静默；重复事件与不同会话隔离，两个标记不覆盖评估正文。
- 非阻断：匹配工具失败仍能标记；文件故障与知识服务离线时工作正常结束；两个新增 Hook 与记录 CLI 不阻断、不发起模型调用、不写 Asset/Usage、不访问知识数据库。既有 UserPromptSubmit 的能力签发另按原契约回归。

复用当前临时目录测试方式及 [2.4 测试 fixture](../../apps/server/test/multi-expression-recall.test.ts)。旧 `hook.test.ts`、`hook-resilience.test.ts` 仍有 Task/Loadout 断言，不能直接当作当前契约；迁移与本改动相关的 fixture，避免扩大为全仓旧测试清理。

### 7.3 真实 Desktop 验证

安装与信任后，用一次有真实工具活动的普通工程请求刻意遗漏记录：确认活动标记、Stop 警告、正常结束且没有新模型轮次。再核对无工具交流不产生记录或提醒、只读工程审查可评估、code mode/异步命令完成时的实际工具覆盖，以及候选待确认静默结束。人工点名 Skill 成功不证明自动提醒成立。

评估后又出现新结果的样本，应验证主 Agent 更新记录；同时如实保留“Stop 首版无法独立发现同轮过期”的限制。若要求程序保证这一点，需要另行扩大事件观察范围，不能把流程约定的通过当成程序保证。

上线后先抽查少量真实样本的漏评估提醒、无增量误判、候选质量、非工程误提醒及额外耗时，不为统计建立数据库或仪表盘。未覆盖工具或纯对话工程判断仍可能漏提醒。只有漏评估持续存在且提醒不足时，才重新评估是否需要有界补跑；首版不预留重试开关。
