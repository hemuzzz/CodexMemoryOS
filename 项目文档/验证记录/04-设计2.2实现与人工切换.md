## 人工切换顺序

下面命令均未执行。只对明确目标环境执行；不把当前终端环境自动视为正式授权。数据库迁移期间应停止Server、所有同库Hook和旧写进程，暂停旧Hook注册，避免构建过程让旧注册混用新dist。

1. 核对同库写进程并全部停止，暂时禁用旧知识Hook；保留其他Hook与MCP注册。核对真实配置与数据库路径，不能用“端口已停”代替确认全部Hook已停。
2. 在项目根构建匹配版本。构建会更新现有dist，应在前一步完成后进行：

```sh
npx -y -p node@22.16.0 -p pnpm@11.1.3 pnpm build
```

旧 `apps/server/dist/task`、`dist/loadout`、`dist/usage` 是不再生成的产物。停止旧写进程后仅清理这三个旧构建目录，保留知识目录、SQLite及其他用户数据；不得运行遗留旧模块。

3. 为迁移显式设置本机目标（仅示例，先核对）：

```sh
export CODEX_MEMORY_OS_DATABASE_PATH='/Users/hemu/Desktop/github/CodexMemoryOS/knowledge-base/runtime/codex-memory.sqlite'
export CODEX_MEMORY_OS_ASSET_REPOSITORY_PATH='/Users/hemu/Desktop/github/CodexMemoryOS/knowledge-base/repository'
export CODEX_MEMORY_OS_WORKSPACES_PATH='/Users/hemu/Desktop/github/CodexMemoryOS/knowledge-base/config/workspaces.json'
export CODEX_MEMORY_OS_LOG_PATH='/Users/hemu/Desktop/github/CodexMemoryOS/knowledge-base/logs/server.log'
npx -y -p node@22.16.0 -p pnpm@11.1.3 pnpm --filter @codex-memory-os/server knowledge:migrate --offline
```

此命令只新建新版表并将user_version由1升至2，不删除旧三表，不转换旧Usage。新空库使用单独明确的 `knowledge:migrate --offline --initialize`；仅接受不存在/空数据库，不以该选项修复损坏库。数据库父目录须存在。普通服务启动不会自动完成新版迁移。

4. 同批安装仓库内协议包：将三份 `integrations/codex/skills/<name>/SKILL.md` 替换到 Codex home 对应Skill目录；保留各Skill既有agents元数据和其他无关文件。用 `integrations/codex/KNOWLEDGE.md` 替换同home协议；将 `AGENTS-knowledge-section.md` 中的知识规则合并替换原知识节，保留其他全局规则。对比包内manifest记录的旧Hash；运行文件后来有变化时先保留并合并差异，不能盲目覆盖。
5. 合并Hook/MCP示例（本机端口18888），保留其他注册，确认脚本仍指向本仓库新版dist与同一数据库。示例只说明待切换目标，不证明已安装。
6. 启动新版服务，再启用经过检查/信任的新版Hook：

```sh
/bin/sh '/Users/hemu/Desktop/github/CodexMemoryOS/knowledge-base/start-server.sh'
```

重载Codex客户端，使用新上下文核对实际工具目录和Skills，不依赖当前已注入的旧规则。验证 `/health`、`/api/system/status`、Hub和实际MCP链。不得手工伪造Hook输入或插入能力作为宿主验收。

7. **先完成基础真实链与数据保留检查，再决定旧表删除。** 若验收未完成，不执行以下命令。若后来明确决定删除，停全部写进程后执行：

```sh
npx -y -p node@22.16.0 -p pnpm@11.1.3 pnpm --filter @codex-memory-os/server runtime:retire --offline --accept-data-deletion-after-manual-verification
```

删除顺序仅task_asset_usage、task_turn_binding、task_loadout，同事务升至3；失败回滚本次变更。保留正式Markdown、Inbox、配置、Catalog/FTS、asset_content_version、workspace_capability和新事实。不承诺恢复已提交删除的旧运行数据。本轮没有授权执行此步骤。

明确撤销能力时使用 `capability:revoke --digest <数据库中确切摘要>`；工具不输出bearer。无到期清理或续期。映射故障恢复后原授权可重新有效，永久撤销须删除该摘要记录。
